## tessvm에서 알아낸 것 (속도에 큰 것부터)
1. **틱 몰아 실행**: 60틱/초 고정 스텝. 틱이 16.7ms를 넘으면 한 화면에 최대 4틱을 실행한다. 틱 29ms면 34틱/초로 재어지지만 화면은 9번/초. `tm.mjs`의 `ticks/s`만 보면 속는다. 작품 안에서는 `dateSec`로 1초의 틱 수를 세어 57 미만이면 과부하로 본다(프로젝트 타이머는 틱마다 1/60초씩만 간다).
2. **색별 묶음 그리기**: 같은 스타일의 2점 획이 16개 이상 이어지면 메시 하나(`render/segments.js`). 색을 줄 조각마다 바꾸면 8000조각에 그리기 15ms, 색별로 모으면 1.3ms. 획은 `goto, penDown, goto, penUp`.
3. **숫자 상수는 글자**: 블록의 숫자는 `"5"`로 컴파일된다. 변수·리스트에 넣으면 글자로 남아 쓸 때마다 `parseFloat`. `ejs.mjs`를 고쳐 함수 안의 숫자 상수를 진입 때 `(5 - 0)`으로 만든 지역 변수에서 읽게 했다(대입, 비교, 리스트 번호, 호출 인자). `x + 3`은 `x - (-3)`으로(PLUS는 글자 여부를 먼저 본다). 틱 23 → 19ms.
4. **소수는 느리다**: `+ − ×`에 소수가 섞이면 `snap`(자릿수 세기). 나눗셈은 `idiv`, 제곱근은 `idiv(sqrt, 1)`로 바로 정수로.
5. **함수 호출**: 호출 자체는 0.12µs지만 지역 변수 하나에 약 10ns(시작 때 모두 `"0"`으로 채움). 지역 150개면 1.5µs.
6. **큰 함수는 느리다**: 같은 반복이 작은 함수에서는 연산당 2.7ns, `traceCluster` 크기에서는 약 8ns. 드문 경로를 함수로 빼도(`mirrorCell`, `floorShade`) 이득이 없었다 — 호출 비용과 비슷했다. `a + b`를 `a - (0 - b)`로 바꾸는 것(`FASTPLUS=1`)은 더 느렸다.
7. Chrome 154는 같은 코드가 Node 24보다 약 25% 느리다. 헤드리스는 25초쯤 뒤 2배 느려질 때가 있다(창을 띄우면 없음).

## 렌더러 구조
- 카메라 공간에서 추적. 줄마다: 구의 구간(2차식) + 삼각형 구간(투영 변) → 겹침 묶음 → 덮는 물체가 바뀌는 곳에서 나눔 → 각 조각을 간격 격자로 추적.
- 조각 안: 이웃 광선의 "만난 것 표시"(ssig)가 같으면 사이를 중간에서 색 바꿈, 다르면 이분.
- 줄 순서는 `ROWSEQ`: 핵심 줄(2줄 간격)과 그 사이 줄. 사이 줄은 위아래 핵심 줄의 표시가 같으면 색을 가져다 씀(`CS`, `CC`, 프레임·줄 도장 포함).
- 배경: `rowPrep`이 바닥(타일 DDA, 그림자 구간)·하늘(띠 경계)을 `BGX/BGV`로, `bgSeg`가 칠함.
- 조각 저장소 둘(`sBase` 0 / `PALN`): 인터레이스에서 홀수 줄 조각을 한 틱 보관했다가 짝수 줄과 같은 틱에 그림. 펜 B는 `timer() != bTick`으로 "다음 틱"을 안다(두 오브젝트의 실행 순서와 무관).
- 삼각형: 정적 표는 빌드 때. 프레임마다 꼭짓점 변환, 근평면 자르기, BVH 상자 다시 맞추기(`meshSetup`). `bvhHit`는 스택 없이 `BSKIP`을 따라감.

## 수치 (이 PC, 창 띄운 Chrome 154, 시작 화면)
- 3단계(480×270i, 간격 3): 틱 13.9ms + 그리기 1.7~1.9ms, 60틱/초
- 헤드리스(시작 3초 뒤 6초): 1단계 40ms, 2단계 28ms, 3단계 17.7ms, 4·5단계 15ms, 6단계 11.5ms, 7단계 8.6ms
- 광선 약 3000~5000개/틱, 조각 약 3000~3500개/틱, BVH 호출 약 100회/틱

## 안 한 것 / 다음에 할 만한 것
- 순정 엔트리에서 실행 확인(`../gmp/erun.mjs`가 서버를 못 띄워 못 함)
- 간격을 넓히고 표본 사이를 선형 보간(지금은 중간에서 한 번 바꿈)
- 약한 거울(빨강·파랑 구)에 비친 바닥 경계 찾기(`SIGKR`), 지금은 뭉개짐
- 약한 거울은 바닥·하늘만 비추기(`WEAK=1`): 0~8% 빨라지지만 화질 손해라 끔

# v1.alpha (2026-10-05)

요청: "딜레이 제거 코드와 ~인 동안 반복하기 코드를 제거해서 1.alpha 버전을 만들어줘"
산출물: 루트 `엔트리 레이트레이서 v1.alpha.ent`, `엔트리 레이트레이서 v1.alpha 설명서.md`
빌드: `node build.mjs alpha.ent ALPHA=1` → `loops 83, whileBlocks 0, tricks 0, globals 419, functions 106`

- `deloop.mjs`: 매크로를 편 소스에서 `while`을 모두 자기 호출 함수로 바꾼다. 반복과 바깥이 함께 쓰는 지역 변수는 전역(`z함수_이름`)으로, 한 반복의 한 바퀴 안에서 "읽기 전에 반드시 쓰는" 변수는 그 반복함수의 지역으로 둔다(전부 전역이면 틱 44ms, 이렇게 하면 27~31ms; v1.0은 13~14ms). `break`는 표시 변수.
- 확인: `nrun.mjs`로 v1.0과 300틱 뒤 `nsamp, nrun, nused, bvCalls`가 같음. 알파 소스는 Node 시뮬레이터로는 못 돌린다(초기화 재귀 4만 단계가 JS 스택을 넘김).
- 상수 풀을 끄는 것(`POOL=0`)은 이득 없음.
- `src/main.js`에 AUTO 화면 건너뛰기(`skipN`, `drawStep`)를 넣었다. 지금 소스로 `ALPHA` 없이 빌드하면 이 기능이 든 판이 나오고, 루트의 v1.0 파일은 넣기 전 빌드 그대로다. v1.0을 다시 낼 때는 버전을 올릴 것.

# v1.1 (2026-10-05) — 체스 나이트

요청: "최적화 전에 약한 거울 재질의 체스 기물(나이트)를 추가해줘" → "나이트 추가하고 v1.1로 저장"
빌드: `node build.mjs rt.ent` → `NT 176, BN 115, NM 2, functions 24, lists 152`

- `mesh.mjs`: 물체 둘(피라미드, 나이트). 나이트 = 선반 받침(8각 5단 + 뚜껑) + 옆모습 15점을 귀 자르기로 삼각형화해 두께를 준 머리. 삼각형마다 `TKR`(거울), `TMESH`, `TSELF`.
- 물체마다 둘레 구(`NS+1 .. NS+NM`). BVH 뿌리의 두 자식 = 두 물체. SAH 분할, 잎 4개(`BVH_LEAF`; 2~8에서 틱 차이는 10% 안).
- 거울 삼각형: `traceCluster`의 삼각형 경로에서 `triMirror`(함수) 호출 → 구 6개 + 다른 물체(둘레 구에 닿을 때만 BVH, `skip`으로 자기 물체 제외) + 바닥/하늘(`M_env`, 구의 반사와 같은 매크로).
- 나이트를 넣자 틱 13 → 44ms(BVH가 60%: 틱당 2800회, 호출당 노드 21개). 줄인 순서:
  1. 자기 물체 반사 제외 + 그림자 후보 조건 강화: 44 → 21ms
  2. 빌드 때 삼각형별 그림자 분류(표본 91점에 광선): "일부 가려짐" 81 → 32개. 21 → 18.6ms, BVH 틱당 490회
  - 해 봤다가 버린 것: 그림자를 삼각형으로 잘라 얹기(겹치는 쌍마다 조각이 생겨 176 → 510개).
- 지금 시간(Node, 3단계): traceCluster 42%, bvhHit 20%, triMirror 11%, 줄 반복·배경 10%.
- 행 범위 도장은 2^20 단위로 넓힘(물체 번호가 63을 넘음).
- AUTO: 단계 변경 직후 1초는 판정하지 않음. `skipN`(화면 건너뛰기)은 v1.1부터 정식 포함.
- 수치(창 띄운 Chrome, 시작 화면): 3단계 틱 20.2ms(47틱/초), AUTO는 29초 시점 6단계 60틱/초.
- 시험: `node test.mjs` → `PASS worst inside share at stride 1: 0.168%` (카메라 18곳)

# v1.2 (2026-10-05) — 팽이, 스포츠카, 공 하나

요청: "v1.2로 인셉션에 나오는 팽이랑 광나는 스포츠카(실제 있는 차 모델을 저작권 문제 없는걸로 인터넷에서 찾아줘) 추가하고 공은 움직이는거 1개만"
빌드: `node build.mjs rt.ent` → `NV 322, NT 520, BN 335, NM 4` (물체별 삼각형 34/142/80/264)

- 차: `assets/sportsCar.obj`(OpenGameArt, Teh_Bucket, CC0, 우라칸 기반 358개). `mesh.mjs car()`가 읽어 꼭짓점을 합치고 모양으로 색을 나눔(바퀴 = 바퀴 중심 반경 안 + |z| > 0.8, 유리 = 법선으로). 밑면과 바퀴 안쪽 면은 남겨야 한다 — 빼면 바닥에서 쏜 그림자 광선이 "들어가는 면"을 못 찾아 바닥 그림자가 기준과 2.7% 어긋났다. `objview.mjs`는 OBJ 미리보기.
- 팽이: 선반 모양. 물체 이동은 `MOX/MOZ`(물체별)와 `MVM`(꼭짓점의 물체)로 — 꼭짓점, 그림자 점, 둘레 구가 함께 옮겨지고 BVH 상자는 어차피 프레임마다 다시 맞춘다. 회전은 안 됨(법선·색·분류가 빌드 때 값).
- `NS = 1`. BVH 위쪽은 물체 목록을 반씩 나눔.
- 거울 삼각형 법선 `TMX/TMY/TMZ`(×16384, 프레임마다 변에서). ×1024 법선으로는 차 옆면의 스치는 반사가 기준과 0.5% 어긋났다.
- 수치: Node 3단계 틱 25ms(v1.1 18.6). 창 띄운 Chrome 3단계 26ms(37틱/초), AUTO는 31초 시점 7단계 60틱/초(틱 13.8ms).
- 시험: `STRICT=1 node test.mjs` → `PASS 0.316%` (카메라 23곳). 전체 설정은 v1.2 장면으로 다시 돌리지 않았다(오래 걸림).
- 다음(사용자가 예고): 최적화. 지금 줄마다 보이는 면 270개·그림자 다각형 270개를 모두 훑는다(줄 범위 검사). 줄별 목록으로 바꾸는 것이 첫 후보.
