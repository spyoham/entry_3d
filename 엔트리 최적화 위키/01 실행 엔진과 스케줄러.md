# 01. 실행 엔진과 스케줄러 — 블록은 실제로 어떻게 돌아가는가

> 대상: 블록만으로 3D 엔진, 레이트레이서, LLM 추론, 물리 엔진처럼 무거운 엔트리 작품을 만드는 사람
> 소스: `entryjs/src` (github.com/entrylabs/entryjs, commit `e01b81b`, 2026-09-16). 아래 경로는 모두 `src/` 기준이다.
> 표기: **[소스]** = 코드를 직접 읽고 확인함, **[추정]** = 코드에서 추론했거나 브라우저 동작에 기대는 내용(실측 권장).
> 실제로 쓰이는 실행기는 `playground/executors.js`다 (`entry.js:83`의 `require('./playground/executors')`). `playground/executors2.js`는 어디에서도 불러오지 않는 죽은 코드다 **[소스]**.

## 0. 한눈에 보기

## 1. 틱 모델

### 1.1 타이머와 FPS

```js
// class/engine.js:556-563
start() {
    GEHelper.Ticker.setFPS(Entry.FPS);
    if (!this.ticker) {
        Entry.tickTime = Math.floor(1000 / Entry.FPS);
        this.ticker = setInterval(this.update, Entry.tickTime);
    }
}
```

- 틱은 **`setInterval`**로 돈다. `requestAnimationFrame`을 쓰지 않는다 **[소스]**. FPS 60이면 `floor(1000/60) = 16ms`이므로 실제로는 **초당 62.5틱**이다. 서드파티 문서의 실측(180회 반복에 2.87초, 회당 15.9ms)도 16ms 간격과 정확히 맞는다.
- 엔진 티커는 프로젝트를 불러올 때(`util/utils.js:98` → `util/init.js:458-469`) 시작해서 계속 돈다. 정지 상태에서는 `update`가 아무 일도 하지 않는다(`engine.js:579`).
- FPS는 `project.speed`에서 가져온다: `Entry.FPS = project.speed ? project.speed : 60;` (`util/utils.js:55`). 속도 UI는 `[1, 15, 30, 45, 60]`만 허용한다(`engine.js:17`, `:530-534`). 하지만 **프로젝트를 불러올 때는 값의 범위를 검사하지 않는다** **[소스]**. 그래서 JSON의 `speed`를 120처럼 키우면 `tickTime`이 8ms가 된다. 브라우저는 반복 타이머를 약 4ms 아래로 내리지 않으므로 상한은 초당 약 250틱이다 **[추정]**. 플레이엔트리 서버가 이 값을 그대로 저장하고 실행하는지는 확인하지 않았다 **[추정]**. 아래 1.2와 2.4의 부작용(대기 시간이 FPS에 따라 바뀜)도 함께 고려해야 한다.
- 화면 렌더링은 **별도 루프**다. `stage.render`가 `setTimeout`으로 약 16ms마다 돌고, `Entry.requestUpdate`가 켜졌을 때만 실제로 그린다(`class/stage.js:152-160`, `:165-189`). 엔진 틱이 오래 걸리면 같은 메인 스레드에 있는 렌더 타이머도 밀린다 **[추정: 단일 스레드 이벤트 루프]**.

### 1.2 틱 하나에서 일어나는 일

```js
// class/engine.js:578-586
update = () => {
    if (Entry.engine.isState('run')) {
        Entry.container.mapObjectOnScene(this.computeFunction); // 각 오브젝트의 script.tick()
        if (Entry.hw.communicationType !== 'manual') Entry.hw.update(); // 하드웨어가 없으면 바로 return (hw.ts:282-285)
        this._processEngineTimeouts();                                   // 말하기/소리 등의 엔진 시간 타이머
    }
};
```

1. `mapObjectOnScene`이 `[...확장 오브젝트, ...현재 장면 오브젝트]` 배열을 새로 만든다(`class/container.js:863-867`). 장면 오브젝트는 `objects_`의 순서(오브젝트 목록 순서)대로 걸러진다(`container.js:1091-1099`).
2. 각 오브젝트의 `Code.tick()`(`playground/code.js:154-227`)이 그 오브젝트의 `executors` 배열을 앞에서부터 돈다.
   - 일시정지된 실행기(Promise를 기다리는 중)는 건너뛴다(`code.js:170-171`).
   - 끝나지 않은 실행기는 `executor.execute(true)`로 실행한다(`code.js:172-182`).
   - 끝난 실행기는 **그다음 틱에 이 루프가 그 자리를 지날 때** `splice`로 지운다(`code.js:183-189`). 그래서 실행기 목록 정리 비용은 O(실행기 수)다.
3. **클론은 원본 오브젝트의 `Code`를 함께 쓴다.** 원본과 클론의 실행기가 모두 한 오브젝트의 `executors` 배열에 섞여 있다(`code.js:138-139`: `new Entry.Executor(block, entity, this)` 후 `this.executors.push`).

**실행 순서 [소스]**
- 오브젝트 사이: 확장 오브젝트를 먼저 돌고, 그다음 오브젝트 목록 순서대로 돈다(`container.js:863-866`). 오브젝트 목록의 위쪽이 화면 앞쪽인지는 이 영역에서 확인하지 않았다 **[추정]**.
- 한 오브젝트 안: 실행기가 **만들어진 순서**대로 돈다. 시작 이벤트가 오면 엔티티 순서(원본 → 클론들, `container.js:910-927`)와 스크립트 등록 순서(`code.js:131-142`)를 따라 만들어진다.
- 틱 도중에 같은 오브젝트에 실행기가 추가되면(예: 자기 자신을 복제해 생긴 클론의 "복제되었을 때"), 루프가 `executors.length`를 매번 다시 읽기 때문에 **같은 틱에 바로 실행된다**(`code.js:168`). 이미 이번 틱을 마친 오브젝트에 추가된 실행기는 다음 틱에 실행된다.
- 따라서 스레드 간 "경쟁"은 무작위가 아니라 **결정적**이다. 각 스레드는 양보 지점에서만 다른 스레드에게 차례를 넘긴다(협력형 멀티태스킹).

### 1.3 실행기(`Executor.execute`) 한 번이 하는 일

`playground/executors.js:21-149`의 `while (true)` 루프는 **양보 신호가 나올 때까지** 블록을 계속 실행한다. 블록 함수의 반환값에 따라 다음 동작이 정해진다.

| 블록 `func`의 반환값 | 실행기 동작 | 위치 |
|---|---|---|
| `undefined` / `null` / `STATIC.PASS(3)` | 다음 블록으로 간다. 몸체가 끝나면 호출 스택에서 꺼낸다. 꺼낸 스코프의 `isLooped`가 다르면 **양보**한다 | `executors.js:117-136` |
| `STATIC.CONTINUE(1)` (`stepInto` 성공) | 같은 틱에서 몸체의 첫 블록을 계속 실행한다 | `:137-139`, `:190-204` |
| 자기 스코프(`return script`) | **양보**한다. 다음 틱에 같은 블록을 다시 실행한다 (대기 블록이 쓰는 방식) | `:140-143` |
| `STATIC.BREAK(2)` | **양보**한다. 현재 스코프는 그대로 둔다 | `:144-145` |
| `Promise` | 실행기를 `paused`로 표시하고 빠져나간다. Promise가 끝나면 다음 블록으로 넘기고 다음 틱부터 다시 실행한다 | `:75-116` |
| 위 어디에도 해당하지 않는 값 | **아무 분기에도 걸리지 않아 같은 틱에서 루프가 계속 돈다.** 비공식 "무지연 반복" 트릭이 이 틈을 이용한다(2.5 참고) | `:117-146` |

상수는 `util/static.js:26-30`에 정의되어 있다(`RETURN:0, CONTINUE:1, BREAK:2, PASS:3`).

### 1.4 부스트(터보) 모드: `Entry.isTurbo`

```js
// playground/code.js:192-220 (요약)
if (Entry.isTurbo) {
    for (let i = 0; i < loopExecutor.length; i++) {
        ... executor.execute(true) ...
        if (i === loopExecutor.length - 1 &&
            Entry.tickTime > performance.now() - this.isUpdateTime) {
            i = -1; // 처음부터 다시 돈다
        }
    }
}
```

- `loopExecutor`는 이번 틱의 일반 패스에서 `executor.isLooped`가 참인 실행기 목록이다(`code.js:176-178`). `isLooped`는 반복 몸체에서 빠져나오며 양보할 때 켜지고(`executors.js:129-131`), **다시 꺼지지 않는다** **[소스: 리셋 코드 없음]**.
- 시간 예산은 **오브젝트(Code)마다 따로** `tickTime`(16ms)이다. `isUpdateTime`은 `Code.tick` 시작 시 설정되고 끝에서 0으로 돌아간다(`code.js:155-157`, `:222`). 그래서 반복 실행기를 가진 오브젝트가 N개면 틱 하나가 최대 **N × 16ms**까지 걸린다 **[소스에서 추론]**.
- 예산이 남아 있는 동안에는 일시정지되었거나 대기 중인 실행기도 계속 다시 돈다. 예를 들어 `wait_second`는 기다리는 동안 매번 `return script`를 하므로, **기다리기만 하는 반복도 16ms 동안 CPU를 계속 쓴다** **[소스에서 추론]**.
- 함수 호출 블록(`function_general`)은 몸체 안의 반복이 양보하면 `BREAK`를 돌려준다(`block_func.js:403-404`). 이 경로에서는 **호출한 실행기의 `isLooped`가 켜지지 않는다.** 그래서 "시작하기 → 메인함수()"처럼 반복 없이 함수만 부르는 스레드는 부스트 모드에서도 틱당 반복 1회밖에 진행하지 못한다 **[소스에서 추론, 실측 권장]**. 호출하는 쪽 스레드가 진짜 반복 블록의 몸체를 한 번이라도 끝까지 마쳐야 `isLooped`가 켜진다.
- `Entry.isTurbo`를 설정하는 코드는 entryjs 안에 없다(검색 결과 읽는 곳만 있음). 플레이엔트리 페이지(호스트)가 켜는 "부스트 모드"로 보인다 **[추정]**.

## 2. 무엇이 양보를 일으키나 (다음 틱으로 넘어가는 지점)

### 2.1 반복문이 양보하는 정확한 원리

```js
// playground/executors.js:122-132
this.scope = new Entry.Scope(this.scope.block.getNextBlock(), this);
...
if (this.scope.block === null) {           // 몸체(문장 묶음)의 끝
    if (this._callStack.length) {
        const oldScope = this.scope;          // block이 null인 새 스코프 → isLooped === undefined
        this.scope = this._callStack.pop();   // 반복/조건 블록의 스코프로 복귀
        if (this.scope.isLooped !== oldScope.isLooped) {
            this.isLooped = true;
            break;                            // ← 양보
        }
    } else break;                             // 스레드 끝
}
```

- 반복 블록(`repeat_basic`, `repeat_inf`, `repeat_while_true`)은 몸체에 들어가기 전에 `script.isLooped = true`를 설정한다(`block_flow.js:136`, `:203`, `:291`). 몸체가 끝나 반복 블록으로 돌아오면 `true !== undefined`가 되어 **양보**한다.
- `_if`와 `if_else`는 `isLooped`를 쓰지 않고 `isCondition`을 쓴다(`block_flow.js:401-413`, `:474-487`). 그래서 `undefined !== undefined`가 거짓이 되어 **양보하지 않고** 같은 틱에서 계속 진행한다.
- 다음 틱에는 반복 블록의 `func`가 다시 호출되어 횟수를 줄이거나 조건을 다시 확인한 뒤 몸체로 들어간다.

**반복 비용 계산 [소스에서 추론]**
- `n번 반복하기` 하나: 몸체 n회 = **n틱**이다. 마지막 확인(`iterCount === 0`)은 n+1번째 틱의 맨 앞에서 일어나고, 반복 다음 블록도 같은 틱에서 바로 이어 실행된다.
- 중첩 반복 `바깥 m회 { 안쪽 n회 { … } }`: 안쪽 반복이 끝나는 틱은 몸체를 실행하지 않고 바로 바깥 몸체 끝으로 가서 양보한다. 그래서 **(n+1) × m틱**이 든다.
- `계속 반복하기`처럼 몸체가 **비어 있는** 반복: `stepInto`가 `BREAK`를 돌려주므로 역시 1틱에 1회다(`executors.js:195-198`).

### 2.2 블록별 양보 여부 정리

| 블록/구조 | 양보? | 상세 | 근거 |
|---|---|---|---|
| `n번 반복하기` | 반복 1회마다 | 반복할 때마다 **횟수 인자를 다시 계산**한다(값은 버림) | `block_flow.js:133-150`, `scope.js:192` |
| `계속 반복하기` | 반복 1회마다 | | `block_flow.js:202-205` |
| `~인 동안/~이 될 때까지 반복하기` | 반복 1회마다 | 조건은 매 반복 시작 시 계산한다. 처음부터 거짓이면 양보 없이 지나간다 | `block_flow.js:285-294` |
| `만일 ~라면`, `만일 ~라면 / 아니면` | 하지 않음 | 몸체가 끝나면 같은 틱에서 다음 블록으로 간다 | `block_flow.js:401-413`, `:474-487` |
| **빈 가지**(내용이 없는 `만일`/`아니면`으로 진입) | **1틱** | `stepInto`가 첫 블록이 없으면 `BREAK`를 돌려준다 | `executors.js:195-198` |
| `반복 중단하기`(`stop_repeat`) | 하지 않음 | `breakLoop()` → `PASS` → 반복 다음 블록으로 바로 간다 | `block_flow.js:324-326`, `executors.js:213-225` |
| `이번 반복 건너뛰기`(`continue_repeat`) | **1틱** | `continueLoop()`가 `BREAK`를 돌려준다 | `block_flow.js:348-350`, `executors.js:227-241` |
| `~초 기다리기` | 최소 1틱 | 첫 호출에서 `setTimeout`을 걸고 `return script` 한다. 그 뒤 매 틱 깃발을 확인한다. **0초여도 1틱**을 쉰다. 기다리는 동안 매 틱 초 인자를 다시 계산한다 | `block_flow.js:47-73` |
| `~이 될 때까지 기다리기` | 조건이 거짓인 동안 매 틱 | 처음부터 참이면 양보 없이 지나간다 | `block_flow.js:548-555` |
| `신호 보내기` | 하지 않음 | 하지만 수신자 실행은 `setTimeout`으로 미뤄진다(5장) | `block_start.js:413-426` |
| `신호 보내고 기다리기` | **최소 1틱** | 수신 스레드가 모두 끝날 때까지 매 틱 `return script` 한다 | `block_start.js:500-534` |
| 함수 호출(일반) | 몸체가 양보하지 않으면 **하지 않음** | 몸체가 양보하면 호출 블록도 양보하고, 다음 틱에 이어서 실행한다 | `block_func.js:378-411` |
| 함수 호출(값 반환) | 몸체가 양보하지 않으면 **하지 않음** | 몸체가 양보하면 rAF 비동기로 넘어가고 호출자는 일시정지된다 | `block_func.js:453-495`, `code.js:587-622` |
| 빈 함수(몸체 없음) 호출 | 1틱 | `function_create`의 `stepInto`가 `BREAK`를 돌려준다 | `block_func.js:662-671`, `executors.js:195-198` |
| `복제본 만들기` / `이 복제본 삭제하기` | 하지 않음 / 스레드 종료 | | `block_flow.js:774-786`, `:824-830` |
| `멈추기` 계열 | `die()` → `BREAK`, 스레드 종료 | | `block_flow.js:598-...`, `scope.js:182-185` |
| Promise를 돌려주는 블록이나 값 | 결과가 나올 때까지 그 스레드만 멈춤, 최소 1틱 | `Scope.run`이 `Promise.all(values)`로 감싼다 | `scope.js:192-208`, `executors.js:75-116` |

### 2.3 한 틱 안에 많은 일을 시키는 방법 (공식 동작 범위)

1. **반복 대신 "양보 지점이 없는 함수"를 쓴다.** 일반 함수와 값 반환 함수 모두 몸체에 반복, 대기, 빈 가지, `continue`, `신호 보내고 기다리기`가 없으면 `funcExecutor.execute()` 한 번으로 끝까지 동기 실행된다(`block_func.js:393`, `:475`). 이렇게 끝나면 호출한 블록은 `undefined`나 값을 돌려주고 같은 틱에서 계속 진행한다.
2. **반복을 재귀로 바꾼다.** 재귀 호출도 같은 경로로 동기 실행된다. 꼬리 재귀가 아니어도 동기 실행이다. 깊이는 JS 스택이 허용하는 만큼만 가능하다(2.4).
   - "반복 m회"를 "재귀 깊이 m"으로 바꾸는 대신, 깊이를 줄이는 방법도 있다. 예를 들어 함수 하나가 몸체 안에서 일을 k번 펼쳐서(복사해서) 하고 자기 자신을 m/k번 재귀 호출하게 하면 된다. 이분할 재귀(앞 절반 처리 + 뒤 절반 처리)를 쓰면 깊이가 log₂(m)로 줄어든다 **[소스에서 추론]**.
3. **블록을 직선으로 펼친다.** 양보 지점이 없는 블록 열은 몇 개든 한 틱에 실행된다. 단, 긴 블록 열에는 O(n²) 비용이 있다(3.3).
4. **부스트 모드**: 1.4의 조건을 만족하는 반복 스레드에서만 효과가 있다.
5. **(위험) `project.speed`를 키운다**: 1.1 참고. 틱 수 자체가 늘어난다. 하지만 `~초 기다리기`의 실제 시간이 `60/fps`배로 짧아진다(`block_flow.js:52-53`). 이동 블록은 `frameCount = time × FPS`로 계산하므로 실제 시간이 유지된다(`blocks/block_moving.js:542`) **[추정: 사이트 동작 미확인]**.

### 2.4 숨은 한도와 경고

- **반복 횟수 한도 없음.** 일반 모드에는 틱당 시간 예산도 없다. 한 스레드가 1초짜리 동기 계산을 하면 그 틱 전체와 화면 렌더링이 1초 멈춘다 **[소스: 감시 코드 없음]**.
- **재귀 한도**: `Entry.callStackLength`는 증가(`block_func.js:381`, `:456`)와 감소(`:410`, `:491`)만 하고 **어디서도 검사하지 않는다**. 실제 한도는 JS 스택 크기다.
  - 일반 함수 재귀 한 단계는 대략 `Executor.execute → Scope.run → function_general.func → Executor.execute` 정도의 JS 프레임을 쓴다. 값 반환 함수는 `getParams`/`map` 콜백이 더해져 더 많이 쓴다. 크롬 기준 재귀 깊이는 **수천 단계 수준**으로 보인다 **[추정, 실측 권장]**.
  - 스택이 넘쳐 `RangeError`가 나면 `catch`가 받는다. 함수 실행기 안이라면 `isFuncExecutor` 분기가 먼저 걸린다. 이때는 "재귀 호출 경고" 토스트 없이 일반 런타임 오류로 **프로젝트 정지**가 된다(`executors.js:57-64`). 재귀 경고 토스트는 함수가 아닌 실행기에서 난 `RangeError`에만 뜬다 **[소스]**.
- **어떤 블록이든 예외를 던지면 프로젝트가 정지한다**(`executors.js:65-67` → `Entry.Utils.stopProjectWithToast`, `util/utils.js:2160-2172`에서 `engine.toggleStop()`).
- **`~초 기다리기`는 FPS에 따라 늘어난다**: `timeValue = (60 / fps) * timeValue * 1000` (`block_flow.js:52-53`). FPS 30에서 "1초 기다리기"는 실제로 2초다.
- **클론 한도**: `Entry.maxCloneLimit = 360` (`util/init.js:63`). 검사식이 `clonedEntities.length > maxCloneLimit`이라 오브젝트당 361개까지 만들어진다(`class/object.js:541`).

### 2.5 "무지연 반복" 트릭 — 우리 작품들의 핵심 기법

서드파티 문서(`07-runtime-quirks.md` 1003행 이하)에 나오는 트릭은 현재 소스에서도 그대로 동작한다 **[소스로 메커니즘 확인]**.

- 형태: 반복 몸체의 마지막에 `~이 될 때까지 기다리기( 아니다( 이번 반복 건너뛰기 ) )`를 둔다.
- 원리:
  1. 이 블록의 인자를 계산하는 중에 `continueLoop()`가 실행기의 스코프를 반복 블록으로 되감고 `BREAK(2)`라는 **값**을 돌려준다.
  2. `아니다(2)`가 거짓이므로 `wait_until_true`가 `return script`를 한다. 이때 돌려주는 것은 되감기 전의 낡은 스코프다.
  3. 1.3 표의 "아무 분기에도 걸리지 않는 값"이 되므로 같은 틱에서 다음 반복으로 넘어간다(`executors.js:117-146`, `:227-241`, `scope.js:192`).
- 또 다른 변종: 미로 전용 `ai_repeat_until_reach`(`playground/block_entry.js:7387-7411`)는 `isLooped`를 설정하지 않고 `stepInto`만 한다. 그래서 몸체가 끝나도 양보하지 않는다.
- 실제 사용: 레이싱·레이트레이서·GMP 등 우리 작품의 무거운 반복은 거의 모두 이 트릭을 쓴다(`05 실측 교훈 모음.md` 4장, `_work/gmp/doc.md:130`, `3D 레이싱 기술 설명.md` §1). tessvm도 이 모양을 알아보고 양보 없는 `continue`로 컴파일한다(`04 tessvm.md` 1.3).
- 주의: 반복 몸체의 **모든 경로 끝**에 있어야 한다(중간 경로가 그냥 끝나면 그 바퀴는 1틱 쉰다). 엔진 내부의 빈틈에 기대므로 엔트리가 실행기를 고치면 깨질 수 있다. 도는 동안 화면이 멈추고, 탈출 조건이 없으면 탭이 멈춘다.
- 재귀와 비교: 엔트리 공식 동작만으로는 재귀(2.3)가 대안이지만, tessvm에서는 이 트릭 쪽 while이 재귀보다 약 2배 빨랐다(`05` 4장 "재귀 vs while").

## 3. 블록 하나를 실행하는 데 드는 고정 비용

### 3.1 명령 블록 하나 (실행기 루프 1회)

`executors.js:37-136` 기준으로 블록마다 다음 일이 일어난다.

1. `executedBlocks.push(block)`: 실행한 블록을 **모두** 배열에 쌓는다. 감시 리스너가 없으면 이 배열은 쓰이지도 않는다(`executors.js:39`, `code.js:179-182`). 한 번의 `execute` 안에서 블록을 100만 개 실행하면 원소 100만 개짜리 배열이 생긴다.
2. `try { … } catch`
3. `block.getSchema()`(캐시됨, `playground/block.js:141-147`), `schema.class === 'ai_learning'` 비교, `Entry.skeleton[schema.skeleton].executable` 조회
4. `Entry.dispatchEvent('blockExecute', view)`: 리스너가 없으면 lodash `_.isEmpty` 확인 후 바로 반환한다(`util/eventHandler.js:26-38`). 블록 하이라이트 리스너(`Entry.Utils.bindBlockExecuteFocusEvents`, `util/utils.js:2948-2957`)는 **이 저장소 안에서 아무도 호출하지 않는다** **[소스]**. 호스트가 호출하는지는 모른다 **[추정]**.
5. `scope.run(entity)` → 3.2
6. `this.scope.key = Entry.generateHash()`: **블록마다 `Math.random().toString(36).substr()` 문자열 하나를 만든다**(`executors.js:48`, `util/utils.js:953-955`). 이 값을 읽는 곳은 소스(하드웨어 제외)에 없다.
7. 다음 블록으로 갈 때: `new Entry.Scope(getNextBlock())`. 스코프 객체를 하나 만들고 `valueMap = {}`, `valueState = {}` 객체 두 개를 새로 만든다(`executors.js:122-124`).

추가로 **`execute()`를 한 번 부를 때마다**(매 틱, 그리고 **함수를 호출할 때마다**) `window.location.href.indexOf('file://')`를 계산한다(`executors.js:36`). 함수 호출이 수십만 번이면 이 비용도 누적된다 **[추정: location.href 접근이 공짜는 아님]**.

### 3.2 인자 계산 경로: `Scope.run` → `getParams`

```js
// playground/scope.js:187-209
run(entity, isValue) {
    const schema = this.block.getSchema();
    if (this.isCondition) return schema.func.call(this, entity, this); // 만일 블록 재진입만 예외
    const values = this.getParams();                       // ★ 모든 인자를 먼저 전부 계산
    const isPromise = values.some((v) => v instanceof Promise);
    if (!schema.func) return;
    if (!isPromise) { this.values = values; return schema.func.call(this, entity, this); }
    return Promise.all(values).then(...);
}
```

- **모든 인자를 항상, 먼저 계산한다**(`scope.js:36-46`). 인자가 블록이면 `new Entry.Scope(param)` → `run()`으로 재귀한다. 그래서:
  - `그리고/또는`은 **단락 평가를 하지 않는다**. 양쪽을 다 계산한다(서드파티 문서 130행과 일치).
  - **같은 블록에 다시 들어갈 때도 인자를 다시 계산한다.** 대상: `n번 반복하기`의 횟수(매 반복), `~초 기다리기`의 초(대기 중 매 틱), 함수 호출 블록의 인자(몸체가 양보한 뒤 이어서 실행할 때마다). 다시 계산한 값은 버린다. 인자에 값 반환 함수가 있으면 **그 함수가 다시 호출된다**. 예외는 `만일` 블록이 몸체에서 돌아올 때뿐이다(`isCondition`, `scope.js:189-191`).
- **숫자나 글자 상수도 완전한 블록이다.** `number` 블록은 `getField('NUM')`(문자열)을 돌려주는 블록이다(`playground/block_entry.js:973-975`). 상수 하나에도 스코프 생성, `params.map`, `some`, `func` 호출이 일어난다.
- 블록이 아닌 인자(드롭다운 값 등)는 매번 `filterReservedKeywords`를 거친다(`scope.js:29-34`: `typeof` 확인과 `Set.has`, 객체라면 `String()` 변환).
- `values.some(... instanceof Promise)`: 블록마다 인자 수만큼 확인한다.

**값을 꺼낼 때의 변환** (`scope.js:93-150`)

| 메서드 | 동작 | 주의 |
|---|---|---|
| `getValue(key)` | `this.values[paramsKeyMap[key]]` | 변환 없음 |
| `getNumberValue` | `parseFloat(v) \|\| 0` | NaN은 0이 된다. 상수 블록은 문자열이라 **매번 parseFloat** 한다 |
| `getStringValue` | `String(v)` | |
| `getBooleanValue` | `undefined`면 false. 아니면 `Number(v)`가 NaN이면 `true`, 아니면 그 숫자 | `""`, `"0"`, `"0.00"`은 거짓이다. `"abc"`나 `"false"`는 **참**이다 |
| `getField` | `params[idx]`를 `filterReservedKeywords`에 통과시킨 값 | |

### 3.3 다음 블록 찾기는 O(위치)

```js
// playground/thread.js:201-203
getNextBlock(block) { return this._data.at(this._data.indexOf(block) + 1); }
// core/collection.js:85-87 — Collection은 진짜 배열이 아니라 배열 비슷한 객체
indexOf(obj) { return Array.prototype.indexOf.call(this, obj); }
```

- 블록 하나를 넘어갈 때마다 **그 문장 묶음(스레드)의 처음부터 선형 탐색**한다. 블록 n개짜리 직선 열을 한 번 실행하면 비교가 약 n²/2번 일어난다 **[소스]**.
- 문장 묶음의 경계는 반복이나 조건 블록의 몸체, 그리고 함수 몸체다(각자 별도의 `Thread`다). 긴 펼친 코드를 `만일 <참>` 몸체나 함수 여러 개로 나누면 n을 줄일 수 있다. 실제로 얼마나 빨라지는지는 측정이 필요하다(배열 비슷한 객체에서 `indexOf` 비교 한 번은 수 ns 수준) **[추정]**.

### 3.4 예외 처리

- 블록 하나하나가 `try/catch` 안에서 실행된다. 예외가 나면 **프로젝트 전체가 정지**한다(`executors.js:50-68`). 범위를 벗어나는 글자/리스트 접근처럼 예외를 던지는 블록은 반드시 조건으로 감싸야 한다.
- 비동기 대기용 `AsyncError`만 예외적으로 `BREAK` 처리된다(`executors.js:51-52`).

## 4. 함수 호출 비용

### 4.1 일반 함수(`function_general`) 호출 흐름

`blocks/block_func.js:378-411`

```js
if (!this.initiated) {                                   // 호출 블록의 스코프마다 1회
    this.initiated = true;
    Entry.callStackLength++;
    const func = Entry.variableContainer.getFunction(this.block.getFuncId()); // O(1) 해시
    this.funcCode = func.content;
    this.funcExecutor = this.funcCode.raiseEvent('funcDef', entity)[0];     // 새 Executor
    this.funcExecutor.register.params = this.values;    // 인자 배열을 그대로 넘김
    this.funcExecutor.register.paramMap = func.paramMap;
    ...
    this.funcExecutor.localVariables = _cloneDeep(func.localVariables);     // 지역변수 깊은 복사
}
const { promises } = this.funcExecutor.execute();      // ★ 동기 실행
if (!this.funcExecutor.isEnd()) {                        // 몸체가 양보했다면
    if (promises.length) return Entry.Code.funcAsyncExecute(...);
    this.funcCode.removeExecutor(this.funcExecutor);
    return Entry.STATIC.BREAK;                           // 호출자도 양보, 다음 틱에 이어서
} else this.funcCode.removeExecutor(this.funcExecutor);
Entry.callStackLength--;
```

**호출 1회당 고정비 [소스]**
1. 호출 블록의 인자를 모두 계산한다(3.2).
2. `funcCode.raiseEvent('funcDef', entity)`: 함수 Code의 `funcDef` 이벤트 블록마다 `block.pointer()`를 계산한다. 이때 배열을 만들고 스레드 `indexOf`와 코드 `indexOf`를 한다(`code.js:123-144`, `thread.js:261-278`). 그 뒤 **`new Entry.Executor`**를 만들고(스코프, 배열, 객체 다수, `generateId()` 난수 문자열, `executors.js:6-19`) 함수 Code의 `executors`에 넣는다.
3. `_cloneDeep(func.localVariables)`: 지역변수 수에 비례한다. 지역변수 사용 설정을 꺼도 배열이 있으면 복사한다(`class/function.js:14-20`).
4. `execute()` 1회: 3.1의 `location.href` 계산 등이 포함된다.
5. **함수 머리 체인을 두 번 계산한다.** `function_create` 블록의 첫 인자는 `function_field_label → function_field_string/boolean → …`으로 이어진 블록 체인이다. `Scope.run`은 `func`보다 먼저 이 체인을 전부 계산한다(`scope.js:192`). 함수에 처음 들어갈 때 한 번, 몸체가 끝나 돌아올 때(`isFunc` 분기, `block_func.js:662-671`) 또 한 번 계산하므로 **매개변수 수에 비례하는 비용이 두 번** 든다 **[소스에서 추론]**.
6. 끝나면 `removeExecutor`(`indexOf`와 `splice`, `code.js:229-234`).

**양보할 때**: 몸체 안에서 반복이 한 바퀴 돌면 호출자 스레드도 그 틱을 마친다. 다음 틱에 같은 호출 블록을 다시 실행하면 `initiated`가 이미 참이라 이어서 실행한다. 다만 **호출 블록의 인자는 다시 계산된다.** 다시 계산한 값은 버려지고, 함수는 처음 계산한 `register.params`를 계속 쓴다 **[소스]**.

### 4.2 값 반환 함수(`function_value`)

`blocks/block_func.js:453-495`

- 초기화는 4.1과 같다. 그다음 `function_create_value` 블록을 **건너뛰고** 몸체의 첫 블록부터 실행한다(`:470-474`).
- 동기로 끝나면 `function_create_value` 스코프에서 `getParams()`로 **반환값 식(과 머리 체인)**을 계산해 돌려준다(`:492-494`).
- **몸체가 양보하면**(반복, 대기, 빈 가지 등) `Entry.Code.funcRestExecute`로 넘어간다(`code.js:587-622`). 이 함수는 `requestAnimationFrame`마다 `funcExecutor.execute()`를 한 조각씩 실행하는 **Promise**를 돌려준다.
  - 그 결과 호출한 명령 블록의 `Scope.run`이 `Promise.all` 경로를 타고, 호출자 실행기는 **일시정지(paused)**된다(`scope.js:198-208`, `executors.js:75-116`).
  - 반복 1회 = rAF 1회다. rAF 주기는 엔진 틱과 별개로 **모니터 주사율**을 따르고, 백그라운드 탭에서는 멈춘다 **[추정: 브라우저 동작]**. 부스트 모드의 혜택도 받지 못한다.
  - **결론: 값 반환 함수 안에는 반복이나 대기를 넣지 않는다.**

### 4.3 매개변수, 지역변수, 전역변수 읽기 비용

| 종류 | 블록 | 조회 방식 | 비용 |
|---|---|---|---|
| 함수 매개변수 | `function_param_string/boolean` | `this.executor.register.params[paramMap[this.block.type]]` | **O(1)**, 가장 싸다 (`block_func.js:601-605`, `:622-626`) |
| 함수 지역변수 읽기 | `get_func_variable` | `getField` → `variableId.split('_')`(문자열 배열 생성) → `getFunction` → lodash `_find`로 지역변수 배열을 선형 탐색 | O(지역변수 수) (`block_func.js:261-266`, `class/function.js:180-186`) |
| 함수 지역변수 쓰기 | `set_func_variable` | 위와 같은 방식(`split`, `_find`) | O(지역변수 수) (`block_func.js:160-169`, `function.js:188-194`) |
| 전역/오브젝트 변수 | `get_variable` 등 | `_.find(this.variables_, { id_ })`: lodash 매처로 **모든 변수**를 선형 탐색. 클론의 오브젝트 변수라면 한 번 더 탐색 | O(전체 변수 수) (`class/variable_container.js:1353-1361`) |

- 지역변수를 읽을 때 `localVariable?.value || 0`을 돌려준다(`function.js:185`). **빈 문자열이나 `false`를 저장하면 0으로 읽힌다** **[소스]**.
- 매개변수는 읽기만 가능하고 쓸 수 없다. 하지만 "읽기만 하는 값"이라면 전역변수보다 훨씬 싸다. 재귀 함수의 상태를 매개변수로 넘기는 패턴이 성능 면에서도 유리하다.
- 전역변수 조회는 `variables_` 배열 앞에서부터 찾는다. 그래서 자주 쓰는 변수가 배열 앞쪽(먼저 만든 변수)에 있으면 조금 더 빠를 것이다 **[추정: 배열 순서 = 생성 순서라고 가정]**. 변수 수 자체를 줄이는 효과가 더 확실하다.

### 4.4 재귀

- 재귀는 동기로 실행되므로 2.3의 "반복을 한 틱 안에서" 하는 핵심 수단이다. 깊이 한도와 오류 동작은 2.4를 보라.
- 함수 Code 하나의 `executors` 배열은 재귀 깊이만큼 길어진다. 호출마다 `raiseEvent`가 `push`하고, 끝나면 `removeExecutor`가 `indexOf`와 `splice`를 한다. 깊이 d면 해제 비용은 O(d)다.
- 서드파티 실측: `fibnaive(28)`(약 83만 호출)에 11.5초, 즉 **호출 1회당 약 14µs**(본문의 비교, 덧셈, 변수 쓰기 포함)다. 블록 한 개 수준의 일을 하는 함수는 호출 고정비가 본문보다 크다. **아주 작은 함수는 인라인(펼치기)하는 편이 낫다** **[추정: 문서의 실측과 4.1의 고정비 목록으로 판단]**.

## 5. 신호(메시지)와 이벤트

### 5.1 `신호 보내기`

```js
// blocks/block_start.js:413-426
const value = script.getField('VALUE', script);
const isExist = Entry.isExist(value, 'id', Entry.variableContainer.messages_); // 신호 목록 선형 탐색
if (value == 'null' || !isExist) throw new Error(...);
setTimeout(() => { Entry.engine.raiseMessage(value); });   // ★ 비동기
```

```js
// class/engine.js:1247-1253
raiseMessage(value) {
    Entry.message.notify(Entry.variableContainer.getMessage(value)); // _.find
    return Entry.container.mapEntityIncludeCloneOnScene(this.raiseKeyEvent, ['when_message_cast', value]);
}
```

- **전달 시점**: `setTimeout`이므로 현재 틱이 끝난 뒤 실행기들이 만들어지고, **다음 틱**에 모든 수신 스크립트가 함께 시작된다 **[소스]**.
- **팬아웃 비용**: 현재 장면의 **모든 엔티티(클론 포함)**마다 `code.raiseEvent('when_message_cast', entity, value)`를 부른다(`container.js:910-927`, `engine.js:1029-1031`). `raiseEvent`는 그 오브젝트의 `when_message_cast` 블록마다 `block.pointer()`를 계산하고 `params.indexOf(value)`를 확인한다(`code.js:131-142`). 비용은 **O(엔티티 수 × 그 오브젝트의 수신 스크립트 수)**이고, 받는 엔티티마다 `new Executor`가 생긴다.
- **중복 실행**: 같은 신호를 또 보내도 기존 수신 스레드를 다시 시작하지 않는다. **새 실행기를 하나 더 만든다**(`code.js:137-141`에 중복 검사 없음). 반복 안에서 신호를 계속 보내면 같은 핸들러가 겹겹이 동시에 돈다 **[소스]**.
- 클론도 원본의 수신 스크립트를 실행한다(엔티티마다 실행기가 생김).

### 5.2 `신호 보내고 기다리기`

`block_start.js:500-534`
- 첫 호출에서 `raiseMessage`를 **동기로** 부르고, 돌려받은 **모든 엔티티의 모든 실행기**를 `runningScript`에 모은다(`:522-531`). 그다음 `return script`로 양보한다.
- 그 뒤 매 틱 `runningScript`를 훑으며 끝난 실행기를 빼고, 비면 다음 블록으로 간다(`:501-514`).
- 수신 핸들러가 즉시 끝나도 **최소 1틱**이 든다. 수신 오브젝트가 오브젝트 목록에서 보낸 쪽보다 뒤에 있으면, 핸들러는 같은 틱에 먼저 실행될 수 있다(1.2의 순서 규칙).
- 동기 작업을 신호로 나누면 신호마다 1틱 이상이 든다. **같은 오브젝트 안의 일은 함수 호출로 바꾸는 편이 낫다.**

`class/object.js:540-579` (`addCloneEntity`)

- `when_clone_start` 실행기 생성: `raiseEventOnEntity(clonedEntity, …)`로 그 오브젝트의 Code에만 바로 전달하므로 O(1)이다(`object.js:558`).
- `addCloneVariables`: 오브젝트 전용 **변수와 리스트를 모두 `clone()`** 한다. 리스트가 크면 그만큼 비싸다(`object.js:662-669`).

### 5.5 `~초 기다리기`의 타이머 관리 비용

- `Entry.TimeWaitManager.add(blockId, …)`는 기다리기 블록이 실행될 때마다 `TimeWait`(진짜 `setTimeout`)를 만들고 전역 배열에 넣는다(`class/time_wait.js:4-11`, `:27-33`).
- 대기가 끝날 때마다 `remove(id)`가 **배열 전체를 `filter`** 한다(`time_wait.js:12-23`, `:54-60`). 클론 수백 개가 동시에 기다리면 O(n²)이다.
- ID로 블록 ID를 쓰므로, 같은 블록을 기다리는 클론끼리는 서로의 기록을 지운다. 그러면 일시정지/재개에서 관리되지 않을 수 있다 **[소스에서 추론]**.

## 7. 작품 제작자를 위한 최적화 규칙 (효과가 큰 순서)

1. **무거운 반복은 한 바퀴마다 쉬지 않게 만든다.** 방법은 둘이다: (가) 몸체 끝에 무지연 트릭(2.5)을 둔 반복 — 우리 작품의 기본, tessvm에서도 가장 빠름, (나) 양보 지점이 없는 함수, 즉 재귀나 펼친 코드(공식 동작).
   - 이유: 반복 블록은 1회마다 1틱(16ms)이다(`executors.js:125-132`). 반면 함수 몸체는 동기 실행된다(`block_func.js:393-410`).
   - 효과: 반복 1000회가 16초에서 수 ms로 줄어든다. 서드파티 실측도 500배 이상 차이를 보였다.
2. **함수와 재귀 본문에서 숨은 양보 지점을 모두 없앤다.** 반복, `~초 기다리기`, `~이 될 때까지 기다리기`, `신호 보내고 기다리기`, `이번 반복 건너뛰기`, **비어 있는 `만일`/`아니면` 가지**, 빈 함수 호출이 모두 해당한다(`executors.js:195-198`, `:227-241`).
   - 특히 `만일/아니면`의 빈 "아니면"은 `만일`만 쓰는 구조로 바꾼다. 이런 지점이 하나라도 있으면 일반 함수는 그 틱을 마치고, 값 반환 함수는 rAF 비동기로 떨어진다.
3. **값 반환 함수 안에는 반복과 대기를 절대 넣지 않는다.**
   - 이유: rAF 경로(`code.js:587-622`)로 넘어가면 반복 1회가 디스플레이 프레임 1회가 되고, 호출자 스레드는 통째로 멈춘다.
4. **중첩 반복을 피한다.** `m × n` 반복은 **(n+1)·m틱**이 든다. 안쪽(가능하면 양쪽 모두)을 재귀나 펼친 코드로 바꾼다(2.1).
5. **틱마다 다시 계산되는 인자에 무거운 식을 넣지 않는다.** `n번 반복하기`의 횟수, `~초 기다리기`의 초, 양보하는 함수의 호출 인자는 재진입할 때마다 다시 계산된다(`scope.js:192`). 미리 변수에 담아 두고 상수나 변수 하나만 넣는다. 값 반환 함수 호출을 넣으면 **함수가 반복될 때마다 다시 호출된다.**
6. **`그리고/또는`은 단락 평가를 하지 않는다.** 비싼 쪽을 바깥 `만일` 안으로 옮겨 필요할 때만 계산되게 한다(`scope.js:192`, `:36-46`).
7. **상태는 함수 매개변수로 넘긴다.** 매개변수 읽기는 O(1)이다(`block_func.js:601-605`). 전역변수는 매번 전체 변수 목록을 선형 탐색한다(`variable_container.js:1353-1361`). 지역변수는 `split`과 `_find`를 거치므로 그 중간이다. 전역변수 수 자체를 줄이는 것도 도움이 된다.
8. **함수 호출 고정비를 줄인다.**
   - 이유: 호출마다 `new Executor`, `pointer()`, `cloneDeep(지역변수)`, `location.href`, 머리 체인 두 번 계산이 든다(4.1).
   - 방법: 블록 몇 개짜리 함수는 펼친다. 매개변수와 지역변수 수는 필요한 만큼만 둔다. 깊은 선형 재귀는 이분할이나 "재귀 1회에 여러 단계 처리"로 깊이를 줄인다. 그러면 호출 수와 스택 위험이 함께 줄어든다.
9. **신호는 계산 수단이 아니라 이벤트 용도로만 쓴다.**
   - `신호 보내기`는 `setTimeout`을 거쳐 다음 틱에 전달된다.
   - 보낼 때마다 모든 엔티티(클론 포함)를 순회하고 실행기를 새로 만든다. 이전 핸들러가 아직 돌고 있으면 겹친다(`block_start.js:423-425`, `engine.js:1247-1253`, `code.js:131-142`).
   - `신호 보내고 기다리기`는 최소 1틱이다. 같은 오브젝트 안의 일은 함수로 처리한다.
10. **매 틱 바뀌는 변수는 화면에서 숨긴다.** 보이는 변수는 값을 쓸 때마다 텍스트 측정과 박스 재계산을 한다(`variable.js:184-237`). 숨겨도 다시 그리기 요청은 남으니, 내부 루프에서는 변수 쓰기 횟수 자체를 줄인다(리스트나 매개변수 사용).
11. **긴 직선 코드는 적당한 크기로 나눈다.** 다음 블록을 찾는 비용이 묶음 길이에 비례하므로(`thread.js:201-203`) 수백 블록 이상의 묶음은 O(n²)이 된다. `만일 <참>` 몸체나 함수 단위로 나누면 줄어든다(효과 크기는 **[추정]**, 측정 권장).
12. **클론은 적게, 오래 쓴다.** 생성할 때 오브젝트 전용 변수와 리스트를 모두 복사하고(`object.js:662-669`), 삭제할 때 실행기 전체를 훑는다(`code.js:242-248`). 상한은 오브젝트당 361개다(`object.js:541`, `init.js:63`). 많은 개체는 클론 대신 리스트와 붓/도장으로 그리는 편이 엔진 부담이 적다.
13. **부스트 모드를 쓴다면**:
    - 무거운 반복은 **한 오브젝트**에 모은다(예산이 오브젝트마다 16ms이기 때문).
    - 기다리는 반복은 없앤다(헛돌기).
    - 호출하는 스레드가 진짜 반복 블록의 몸체를 한 번 이상 마치게 한다. `isLooped` 조건이다(`code.js:176-178`, `:192-220`).
14. **한 프레임만 쉬고 싶을 때는 `0초 기다리기`를 쓴다**(1틱 양보, `block_flow.js:47-73`). 단, 기다리는 시간은 `60/FPS` 배율을 따른다. 프로젝트 속도를 바꾸면 대기 시간도 바뀐다(`block_flow.js:52-53`).
15. **예외가 날 수 있는 블록은 미리 감싼다.** 예외 한 번에 프로젝트 전체가 정지한다(`executors.js:50-68`).
16. **(실험적) 작품 속도(`project.speed`)를 키우면 틱 수가 늘어난다.** 불러올 때 범위를 검사하지 않기 때문이다(`util/utils.js:55`). 하지만 대기 시간과 사이트 호환성이 바뀌므로 검증이 필요하다 **[추정]**.

## 8. `07-runtime-quirks.md`(서드파티 문서) 교차 검증

| 문서의 주장 | 소스와 대조한 결과 |
|---|---|
| 반복 1회 = 1프레임(약 16.67ms) | **일치**. 정확히는 `floor(1000/60) = 16ms` 간격이다(`engine.js:560-561`). 문서 실측 2.87s/180 ≈ 15.9ms도 16ms와 맞는다 |
| `wait_second`의 추가 1프레임 원인 중 하나가 `Entry.engine.isContinue = false` | **불일치**. `isContinue`는 대입만 되고(`block_flow.js:70`) 엔진 어디에서도 읽지 않는다. 늘어나는 원인은 "대기 블록이 틱 단위로 깃발을 확인하는 것"과 "반복 끝의 양보" 두 가지뿐이다 |
| 함수 호출은 반복의 틱 지연을 우회한다 | **일치**. 단, 몸체에 양보 지점이 없을 때만 그렇고, 값 반환 함수뿐 아니라 일반 함수도 마찬가지다(`block_func.js:393-410`) |
| 깊은 재귀는 Entry가 `funcRestExecute`(rAF)로 자동 분할한다 | **소스에 근거 없음**. `funcRestExecute`는 몸체가 양보했을 때만 쓰인다(`block_func.js:477-486`). 양보 지점이 없는 `fibnaive`(픽스처 확인)는 한 틱 안에서 동기로 실행되어 멈춘 것으로 보인다 **[추정]** |
| `RangeError`이면 재귀 경고 토스트를 띄우고 정지 | **부분 일치**. 함수 실행기 안에서 나면 `isFuncExecutor` 분기가 먼저 걸려 경고 토스트 없이 일반 오류로 정지한다(`executors.js:57-64`) |
| `boolean_and_or`는 단락 평가를 하지 않는다 | **일치**. `Scope.run`이 모든 인자를 먼저 계산한다(`scope.js:192`) |
| 신호 핸들러는 "같은 프레임에 일제히" 시작하고 순서는 보장되지 않는다 | **부분 불일치**. `신호 보내기`는 `setTimeout`을 거쳐 **다음 틱**에 모두 시작한다. 순서는 오브젝트 목록 순서와 실행기 생성 순서로 **결정적**이다(`container.js:910-927`, `code.js:168`) |
| `신호 보내고 기다리기`는 "한 리스너만" 기다린다 | **불일치**. 모든 엔티티의 모든 수신 실행기가 끝날 때까지 기다린다(`block_start.js:522-531`, `:501-514`) |
| 신호 핸들러는 클론에도 전달된다(팬아웃) | **일치**(`mapEntityIncludeCloneOnScene`) |
| 여러 `복제되었을 때` 스크립트는 병렬이고 순서가 보장되지 않는다 | **부분 일치**. 양보 지점에서 번갈아 실행되는 것은 맞지만, 순서는 스크립트 등록 순서로 결정적이다 |
| `wait_until_true(not(continue_repeat))` 무지연 트릭 | **일치**. 현재 소스에서도 같은 메커니즘이다(`executors.js:117-146`, `:227-241`). 비공식 동작이지만 우리 작품들이 실제로 쓰는 핵심 기법이다(2.5) |
| 미로 블록 `ai_repeat_until_reach`는 `isLooped`가 없는 반복이다 | **일치**(`block_entry.js:7387-7411`) |

## 부록: 죽은 코드와 함정

- `playground/executors2.js`: 불러오지 않는다. 이 파일에는 `continueLoop`도 없다.
- `Entry.engine.isContinue`: 쓰기만 하고 읽지 않는다(`block_flow.js:70`).
- `Entry.callStackLength`: 세기만 하고 검사하지 않는다(`executors.js:32`, `block_func.js:381,410,456,491`).
- `engine.isState(s)`는 `this.state.indexOf(s) > -1`이다(`engine.js:600-602`). 그래서 `'stopping'` 상태에서 `isState('stop')`도 참이 된다.
- `Code.tick`은 마지막으로 실행한 실행기의 `promises`만 `addPromiseExecutor`에 넘긴다(`code.js:224-226`). 이는 정지 시 대기 처리에만 영향을 준다.
- `Scope._setExecutorValueMap`과 `_setChildBlockState`(`scope.js:48-133`)는 이 저장소 안에서 호출하는 곳이 없다.
