# 04. tessvm: 실행 방식과 빠른 코드 쓰는 법

tessvm(크롬 확장 "tessvm for Entry", 분석한 판 **0.3.9**)은 playentry 작품 페이지의 실행 화면을 자기 실행기로 바꾼다. 엔트리 블록을 해석하지 않고 **자바스크립트 제너레이터 소스로 컴파일**해서 돌리고, 그림은 **PIXI(WebGL)** 로 그린다.
이 문서는 확장 소스(제3자 코드, 읽기만 함)와 지금까지 작품을 만들며 잰 값을 묶은 것이다. 소스를 읽고 짐작한 것은 **(추정)** 으로 표시했다.

## 0. 한눈에 보기

| 항목 | tessvm | 근거 |
|---|---|---|
| 실행 단위 | 틱 = 고정 1/60초. 한 화면에 늦은 틱을 **최대 4개** 몰아 돈 뒤 한 번 그림 | `TV/runtime/engine.js:807-836`, `:310` |
| 시계 | 초시계·`n초 기다리기`가 **틱 수 × 1/60초**. 실제 시간이 아님 | `engine.js:858-860`, `TV/runtime/ops.js:560-566` |
| 컴파일 | 작품 → Tess 소스로 디컴파일 → 다시 엔트리 블록으로 컴파일 → JS 제너레이터 소스 → `new Function` 한 번 | `PG/tess-project.js:38-64`, `engine.js:469-508` |
| 반복 | 반복 블록은 **한 바퀴마다 한 틱 양보**(`yield 0`). `<(다음 반복) 아님>까지 기다리기` 트릭이 있으면 양보 없이 돎 | `TV/compile/codegen.js:750-792` |
| 함수 | 제너레이터 트램펄린(스레드의 자체 스택). 재귀 깊이 100만까지 | `codegen.js:98`, `:1176-1190`, `TV/runtime/model.js:790-827` |
| 사칙연산 | 엔트리 BigNumber(십진) 흉내. 정수끼리 약 3 ns, 소수 섞이면 15–250 ns | `TV/runtime/cast.js:247-334`, `RH:1336-1337` |
| 리스트 | JS 배열 `[{data}]`. 길이 한도 없음(순정은 5000) | `model.js:641`, `ops.js:732-798` |
| 숫자 커널 | 반복 없는 숫자 함수만 JS 커널로 옮김. 확장에는 wasm 없음. 실측으로 **효과 없음** | `TV/kernel/plan.js`, `RI:17-30` |
| 펜 | 프레임마다 그 오브젝트의 획 전체를 다시 묶어 그림. 같은 스타일 2점 선분 16개 이상은 메시 하나 | `TV/render/renderer.js:1445-1542`, `TV/render/segments.js:17` |

가장 큰 세 가지: **(1) 소수 `+ − ×`를 정수로**, **(2) 반복은 무양보 트릭으로**, **(3) 붓 그리기를 같은 스타일끼리 묶기**.

## 1. 실행 구조

### 1.1 작품을 불러오는 길

1. `PG/entry-project.js`가 graphql로 작품 JSON을 받는다.
2. `toTessProject`(`PG/tess-project.js:38-64`): `decompileProject`로 **Tess 텍스트로 바꾼 뒤** `compileProject`로 **다시 엔트리 프로젝트로 컴파일**한다. 실행기가 받는 것은 원본이 아니라 Tess 컴파일러가 새로 만든 블록이다. 옮기지 못한 블록은 `dropped`로 보고된다.
   - 이 왕복 때문에 생기는 차이가 있다(§5): 숫자 모양 초기값이 숫자가 되고, 함수 지역 변수 초기값이 0이 되고, 글상자 배경 기본값이 흰색이 된다.
3. `boot`(`TV/web/boot.js:261-`): PIXI 렌더러(`preference: 'webgl'`, `renderer.js:335`)와 `Vm`을 만들고 `vm.load`.
4. `Vm.compile`(`engine.js:469-508`): `Codegen`이 작품 전체를 **하나의 JS 소스**로 만들고 `new Function('R', source)`로 한 번 컴파일한다.
   - 소스 모양(`codegen.js:302-313`): `const O = R.ops, V = R.variables, …; const F = []; F[0] = function* (e, th, P) {…}; … return { scripts: [function* (e, th) {…}, …], functions: F };`
   - 변수·오브젝트·함수는 컴파일 때 **배열 번호**로 풀린다(`varRef` `codegen.js:877-885`). 이름 찾기 비용이 없다.
5. `installKernel`(`engine.js:517-567`): 조건에 맞는 숫자 함수를 커널로 바꿔 끼운다(§4).
6. 모든 그림·소리를 받은 뒤 시작(`boot.js:330-357`).

확장은 `kernelUrl`을 넘기지 않으므로 wasm 모듈이 없고 **JS 커널**만 쓴다(`boot.js:239-259`, `:310-312`, `PG/player.js:403-413`).

### 1.2 틱과 프레임

```js
// TV/runtime/engine.js:807-836 (요약)
const step = 1000 / this.frameRate;              // 60 → 16.67 ms
this.accumulator += Math.min(timestamp - this.lastTime, step * this.maxCatchUp); // maxCatchUp = 4
while (this.accumulator >= step && ticks < this.maxCatchUp) { this.tick(step); ticks++; }
this.renderer?.flush();                           // 그리기는 화면 한 번에 한 번
```

- `frameRate`는 작품의 `speed`(디컴파일러가 없으면 60을 씀, `TS/decompiler/src/index.js:182`). `DEFAULT_FPS = 64`는 speed가 없을 때만(`engine.js:42`, `:334`).
- 화면 구동은 `requestAnimationFrame`, 탭이 숨으면 Worker 타이머(1000/60 ms)로 계속 돈다(`boot.js:141-227`).
- 틱 하나(`engine.js:858-891`): 시계 += 1/60초 → 1초마다 공유·실시간 변수 저장 → 지금 장면의 오브젝트를 **작품 순서대로** 돌며 각 스레드를 `thread.step()` 한 번 → 이 틱에 보낸 신호를 틱 끝에 한꺼번에 발생(`flushMessages`).
- 스레드 한 번 = 그 스레드가 숫자를 `yield`할 때까지 실행(`model.js:790-827`). **시간 예산은 없다.** 무양보 루프가 오래 돌면 그 틱이 그만큼 길어진다(안전장치는 1000만 바퀴, `codegen.js:80`).

**결과(사용자 측정, `_work/rt/HANDOFF.md:26`):** 틱이 16.7 ms를 넘으면 한 화면에 틱을 몰아 돌린다. 틱 29 ms면 34틱/초로 재어지지만 화면은 약 9번/초다. 그리고 초시계가 틱 수로 가므로 **게임 전체가 슬로모션**이 된다(`RH:1332-1333`). 그래서 작품들은 `현재 초`(실제 시계)로 1초의 틱 수를 세어 dt 배율을 맞추거나(레이싱 `rtK`), 57틱 미만을 과부하로 본다.

### 1.3 블록이 무엇으로 바뀌나 (양보 비용)

| 블록 | 생성 코드 | 프레임 비용 | 근거 |
|---|---|---|---|
| `n번 반복` | `while (i !== 0 && !(i<0)) { i--; 몸통; yield 0; }` | 바퀴마다 1틱 | `codegen.js:750-767` |
| `계속 반복`, `~인 동안 반복` | `while (cond) { 몸통; yield 0; }` | 바퀴마다 1틱 | `codegen.js:501-502`, `:769-792` |
| `다음 반복`(그냥) | `{ yield 0; continue; }` | 1틱 | `codegen.js:537-538` |
| `<(다음 반복) 아님>까지 기다리기` (Tess의 `skip`) | `continue;` + 루프에 회전 감시 | **0** | `codegen.js:174-184`, `:526-532`, `:726-748`; `TS/compiler/src/statement.js:235-241` |
| 값 칸에 `반복 중단하기`를 넣은 블록 | `break;` | 0 | `codegen.js:212-224` |
| `반복 중단하기` | `break;` | 0 | `codegen.js:535-536` |
| `~까지 기다리기` | `while (!cond) { yield 0; }` | 조건이 참이 될 때까지 | `codegen.js:533` |
| `n초 기다리기` | 틱 시계로 셈, 최소 1틱 | `ops.js:560-566` |
| 함수 호출 | `(yield F[i](e, th, [인자…]))` | 0(함수 안에서 양보하지 않으면) | `codegen.js:1176-1190` |
| `신호 보내기` | 큐에 넣고 틱 끝에 발생 | 0 | `engine.js:956-970` |
| `신호 보내고 기다리기` | 즉시 발생 후 받는 스레드가 끝날 때까지 `yield 0` | **최소 1틱** (추정: 발생 직후 바로 검사하므로) | `ops.js:672-677` |

무양보 루프의 생성 코드:

```js
{ let s0 = 0, m0 = O.frame();
while (cond) {
  if (m0 !== O.frame()) { m0 = O.frame(); s0 = 0; }
  else if ((s0 += 1) >= 10000000) { s0 = 0; yield 0; m0 = O.frame(); }
  …몸통…
  continue;          // skip 트릭
  yield 0;           // 트릭에 닿지 못한 경로만 여기로 와서 1틱 양보
} }
```

주의할 점:
- **트릭은 몸통의 모든 경로 끝에 있어야 한다.** `만일` 한쪽에만 있으면 다른 쪽은 바퀴마다 1틱을 쉰다.
- 함수 몸통은 반복 깊이 0에서 다시 시작한다(`codegen.js:333-334`). 반복 밖의 트릭은 `yield 0`(1틱)이 된다(`codegen.js:734`). **함수 안의 트릭은 호출한 쪽의 반복을 건너뛰지 못한다.**
- 사용자 측정: 레이트레이서 v1.alpha에서 무양보 `~인 동안 반복` 83개를 모두 자기 호출(재귀) 함수로 바꾸니 틱 **12.8 → 26.8 ms**(약 2배 느림). 전역 변수가 늘고 바퀴마다 호출이 들기 때문이다(`엔트리 레이트레이서 v1.alpha 설명서.md:13`, `:28-30`).

### 1.4 함수

```js
// codegen.js:346-356 (생성되는 모양)
function* (e, th, P) {
  if (th.depth >= 1000000) return;
  th.depth += 1;
  try {
  const L = {"지역id1": 0, "지역id2": 0, …};   // 호출마다 지역 변수 전부를 담은 객체를 새로 만듦
  fn: { …몸통… }
  return 반환식;                                  // 값 함수
  } finally { th.depth -= 1; }
}
```

- 인자는 배열 `P`로, 읽을 때 `P[번호]`(형 정보 없음 → 쓸 때마다 변환, §2). 지역 변수는 `L["id"]`.
- 호출: 인자 배열 + 제너레이터 객체 하나를 만들어 스레드 스택(`Thread.frames`)에 올린다. JS 스택을 쓰지 않으므로 **재귀가 깊어도 넘치지 않는다**(깊이 100만, `codegen.js:83-98`).
- 사용자 측정(`_work/rt/HANDOFF.md:30-31`): 호출 자체는 약 0.12 µs, **지역 변수 하나당 약 10 ns**(호출할 때마다 모두 채움). 지역 150개면 들어가는 데만 1.5 µs. 추적 함수를 구간마다가 아니라 줄마다 한 번 부르게 바꾼 것만으로 틱 12% 감소(`엔트리 레이트레이서 v1.3.1 설명서.md:46`).
- 사용자 측정: **큰 함수는 느리다.** 같은 반복이 작은 함수에서는 연산당 2.7 ns, `traceCluster` 크기 함수에서는 약 8 ns. 드문 경로를 함수로 빼도 호출 비용과 비슷해 이득이 없었다(`_work/rt/HANDOFF.md:32`). 원인은 V8이 아주 큰 제너레이터 함수를 잘 최적화하지 못하는 것으로 보인다(추정).

### 1.5 신호·복제본·장면

- 신호 발생(`fireEvent`, `engine.js:933-947`)은 지금 장면의 **모든 오브젝트·모든 복제본**을 돌며 스크립트 목록을 훑고, 맞는 것마다 `Thread`(제너레이터)를 새로 만든다. 복제본이 많을 때 신호를 자주 쓰면 비싸다(추정, 소스 기준).
- 복제본 상한 360(`engine.js:43`, `:1107-1110`). 만들 때 작품의 **모든 변수**를 훑어 그 오브젝트 전용 변수를 복사한다(`engine.js:1112-1120`).
- 멈춘 스레드는 표시만 하고 다음 틱에 뺀다(`engine.js:996-1009`).

## 2. 값과 형

### 2.1 값이 담기는 모양

- 값은 그대로 JS 값이다. 숫자는 JS `number`, 글자는 `string`. 변수는 `Variable.value`, 리스트 항목은 `{ data }`(`model.js:626-716`).
- 컴파일러가 값마다 종류(`num`/`str`/`bool`/`any`)를 따라간다. 숫자 칸에 넣을 때:
  - 종류가 `num`이면 `(x || 0)`만(`codegen.js:826-833`).
  - `any`(변수 읽기, 리스트 항목, 함수 인자, 함수 반환, 지역 변수)면 `n(x)` = `typeof x === 'number' ? x || 0 : parseFloat(x) || 0`(`cast.js:10-19`).
  - 즉 **변수에 JS 숫자가 들어 있으면 싸고, 숫자 모양 글자가 들어 있으면 읽을 때마다 `parseFloat`**.
- 상수 접기: 숫자 칸의 리터럴은 컴파일 때 숫자로 접힌다(`codegen.js:828-831`). `x * 0.5` → `C.mulNum(n(…), 0.5)`.

### 2.2 숫자 리터럴은 글자다

Tess 컴파일러는 숫자 블록을 `block('number', [String(value)])`로 만든다(`TS/compiler/src/context.js:234`). 숫자 칸이 아닌 곳에서는 접히지 않고 **글자 `"5"`** 로 남는다.

| 쓰는 곳 | 생성 코드 | 매번 드는 일 | 근거 |
|---|---|---|---|
| `x = 5` (변수 정하기) | `O.setVariable(e, 3, "5")` | 변수에 글자가 저장됨 → 읽을 때마다 `parseFloat` | `codegen.js:566-567` |
| `x + 5` (PLUS) | `C.calcPlus(n…, "5")` | 오른쪽 글자를 숫자인지 한 글자씩 검사 + `parseFloat` | `codegen.js:1146-1147`, `cast.js:340-347` |
| `x < 5` (비교) | `C.cmpLess(…, "5")` | `Number("5")` | `codegen.js:1161-1174`, `cast.js:350-358` |
| `f(5)` (함수 인자) | `F[i](e, th, ["5"])` | 함수 안에서 `P[0]`을 쓸 때마다 `parseFloat` | `codegen.js:1186` |
| `리스트의 5번째 항목` | `O.listValue(e, 7, "5")` | `Number("5")` | `ops.js:180-193` |

- `−`, `×`, `÷`는 숫자 칸(`num()`)을 써서 리터럴이 접힌다. PLUS만 `raw`로 받는다(엔트리 규칙: 한쪽이 숫자가 아니면 이어 붙이기).
- 사용자 측정(`_work/rt/HANDOFF.md:28`): 컴파일러(`ejs.mjs`)가 함수 안 숫자 상수를 진입 때 `(5 - 0)`으로 만든 지역 변수에서 읽게 하고(대입·비교·리스트 번호·호출 인자), `x + 3`을 `x - (-3)`으로 바꾸니 틱 **23 → 19 ms**.
- 반대로 일반 `a + b`를 `a - (0 - b)`로 바꾸는 것(`FASTPLUS=1`)은 더 느렸다(`_work/rt/HANDOFF.md:32`). 두 쪽이 이미 숫자면 `calcPlus`의 검사는 `typeof` 한 번이라 싸다.

### 2.3 `변수 ~만큼 바꾸기`는 글자를 남긴다

```js
// ops.js:710-723
if (cast.isNumber(value) && target.isNumber()) {
  const places = maxFloatPoint([value, current]);              // String(...) 두 번
  target.setValue(cast.addNum(Number(value), Number(current)).toFixed(places));  // 글자로 저장
```

엔트리와 같게 결과를 `toFixed` 글자로 저장한다(카운터가 `1`이 아니라 `"1"`). 다음에 읽을 때마다 `parseFloat`이 들고, `String`·`toFixed`도 매번 든다. 뜨거운 반복 안의 카운터는 `x = x - (-1)` 같은 **정하기**가 낫다(소스 기준, 실측 없음).

### 2.4 사칙연산: 엔트리 십진 계산 흉내 (`cast.js`)

엔트리는 `+ − ×`를 BigNumber로 계산한다(`0.1 + 0.2 = 0.3`). tessvm은 같은 결과를 내려고:

```js
// cast.js:299-305
export function addNum(a, b) {
  const r = a + b;
  if (Number.isInteger(a) && Number.isInteger(b)) return r;   // 빠른 길
  return snap(r, maxTail(r, a, b));                            // 피연산자 소수 자릿수를 세어 반올림
}
```

- `maxTail`/`sumTail`이 두 피연산자의 소수 자릿수를 이분 탐색(`decimalsBelow`, Dekker 곱으로 `toFixed` 없이 검사)으로 센다(`cast.js:115-240`).
- `snap`은 결과 크기에 비해 자릿수 격자가 충분히 거칠 때만 `Number(result.toFixed(places))`를 한다(`cast.js:283-296`). 삼각함수 결과 같은 긴 소수끼리는 대개 여기서 그냥 통과한다.
- 나눗셈 `divNum`은 몫의 절댓값이 0.001 이상이면 그냥 `a / b`(`cast.js:328-334`). 작은 몫은 `toFixed(20)`.
- `몫`(`quotient_and_mod`)·`calc_share`는 `Math.floor(a / b)`(`ops.js:1395-1400`, `codegen.js:956-957`). 십진 처리 없음.
- 옛 사칙연산 블록(`calc_plus/minus/times/divide`)도 같은 함수로 컴파일된다(`codegen.js:958-966`). 순정 엔트리에서는 이 블록이 BigNumber를 거치지 않아 빠르지만(OBJ 렌더러: 매듭 한 장 122 → 108 ms), **tessvm에서는 이득이 없다**(`엔트리 OBJ 렌더러 v1.0 설명서.md:104`).

**사용자 측정 (`bench-cast.mjs`, `RH:1336-1338`, `RI:6-8`, `RI:69-74`)**

| 경우 | 1회 비용 |
|---|---|
| 정수 `+ − ×` | 약 3 ns |
| 긴 소수(삼각함수 결과 등) `+ − ×` | 15–45 ns |
| 짧은 꼬리 소수, **비슷한 두 소수의 뺄셈**(예 `161.86 − 147.66`) | **130–250 ns** (`decimalsBelow` + `toFixed`) |
| 나눗셈(몫 ≥ 0.001) | 쌈 |

- v5 레이싱 프레임의 약 70%가 정점 변환의 이 연산이었다(`RH:1338`). v5.1에서 `cast.js` 함수 전체가 게임 틱의 약 절반(`RH:731`).
- 주범은 "짧은 소수"보다 **상쇄 뺄셈**이다. 소수 꼬리를 길게 만들어도(`LONGK`) 뺄셈은 그대로 느리다. **정수화만이 해법**(`RH:733-734`, `RI:8`).
- 효과: 레이싱 v5.1 일부 정수화로 틱 약 4%(모나코 5.51 → 5.32 ms, `RH:738`). v5.2 물리·AI 정수화로 멜버른 4.24 → 3.97 ms(`RH:715`). v6.1 시야 판정·안개·하늘 정수화로 CPU ×4에서 −7 ~ −13%(`RI:147-159`).
- 함정: 상수 `0.50000000003141593`은 `String`이 15자리로 줄어 꼬리가 짧아져 느린 길을 탔다. 긴 꼬리 상수는 `String(c)`의 소수 자릿수가 16 이상인지 볼 것(`RH:713-714`).
- 레이싱 v6.0(모나코 HIGH): 프레임당 `toFixed` 약 2300번, `decimalsBelow` 약 7300번 → 틱의 10% 안팎(`RI:70-71`). 위치별 표는 `RI:76-89`.

### 2.5 그 밖의 형 규칙

- **PLUS의 이어 붙이기**: 한쪽이 `isNumber`(`/^-?\d+\.?\d*$/`, `cast.js:53-86`)가 아니면 글자 이어 붙이기. `x + "1e-25"`는 이어 붙이기가 된다(`_work/cplot/HANDOFF.md:31`).
- **비교**: 글자면 `Number()`로 바꿔 비교, `==`는 엄격 비교(`cast.js:350-384`). 엔트리처럼 `'1.0' == '1'`이 참(`_work/objr/HANDOFF.md:49`).
- **`그리고`/`또는`은 양쪽을 다 계산한다**(단락 없음): `C.andOf(왼쪽, 오른쪽)`(`codegen.js:1039-1049`, `cast.js:387-393`). 비싼 조건은 `만일`을 겹쳐 쓴다.
- **무작위 수**: 경계에 소수가 있으면 `toFixed(2)` 글자를 돌려준다(엔트리와 같음, `ops.js:1344-1352`). `rand(0.0001, 0.9999)`가 약 0.5% 확률로 `0.00`(`RH:544`). 호출마다 정규식 두 번.
- **글자 블록**은 JS 문자열 함수로 바로 바뀐다(`length`, `indexOf`, `split/join` 등, `codegen.js:981-1013`). `바꾸기`·`개수 세기`·`뒤집기`는 배열을 만든다.
- **함수 지역 변수는 NaN을 못 담는다**(`value || 0`), `''`도 0(`_work/cplot/HANDOFF.md:28`).

## 4. 숫자 커널 — 쓰지 말 것

`TV/kernel/plan.js`는 프레임을 넘기지 않는 숫자 함수를 골라 MoonBit(wasm)과 JS 두 벌로 옮긴다. 조건(`plan.js:9-15`, `:360-377`, `:719-802`):

1. 블록이 계산·비교·`만일`·변수/리스트 읽기·`정하기`/`바꾸기`·리스트 항목 바꾸기·함수 호출뿐일 것. **반복 블록, 리스트 추가·삭제·끼워 넣기, 글자, 무작위는 안 됨.**
2. 쓰는 변수·리스트가 전역이고, 공유·실시간·슬라이드가 아니고, **숫자만** 담을 것.
3. 부르는 함수도 모두 조건을 만족하고, 호출 그래프에 순환(재귀)이 없을 것(`plan.js:881-924`).
4. 리스트 길이는 **불러올 때의 길이**로 고정된다(`length_of_list`도 상수로 접힘, `plan.js:589-601`).

실행할 때(`TV/kernel/bridge.js`):
- 커널 루트를 부를 때마다 커널이 쓰는 **모든 슬롯**을 검사하고, `revision`이 바뀐 변수·리스트는 통째로 다시 복사한다(`bridge.js:158-218`, `:250-266`).
- 리스트 길이가 계획과 다르면 커널 전체가 **영구 정지**(`bridge.js:169-171`, `:261`).
- 처음 24번을 재서 복사 시간이 계산 시간보다 크면 그 루트를 버린다(`bridge.js:22`, `:279-292`).
- JS 커널도 같은 `cast.js` 십진 연산을 쓴다(`TV/kernel/runtime-js.js:99-102`). 아끼는 것은 상자 벗기기와 변수 찾기뿐이다.

사용자 측정(`RI:17-30`, `RH:705-706`):
- 레이싱 v5.1: 함수 311개 중 43개만 커널 대상, 나머지 268개는 대부분 `~인 동안 반복` 때문에 거절.
- 빈 리스트로 저장하고 시작할 때 채우는 방식(`allocLists`) 때문에 첫 호출에서 길이가 달라져 **커널이 한 번도 돌지 않았다**(`runs 0`, `fallbacks 1`).
- 리스트를 미리 채운 시험 빌드: 호출당 커널 안 계산 약 12 µs, 복사 약 170 µs, 기존 JS 약 20 µs → tessvm이 스스로 버림. 틱 4.25 → 4.26 ms. 복사가 0이어도 이득은 틱의 2% 안팎.
- 결론: 보류. 확인 도구 `_work/tessvm/kprobe.mjs`(루트와 거절 이유), `kslots.mjs`(슬롯과 리스트 길이).

### 6.1 실시간 변수 버그 (0.3.9)

`PG/cloud.js`가 엔트리 클라우드 서버와 다른 형식을 쓴다(`_work/tessvm/tessvm-실시간변수-버그.md`).

1. 쓰기: `{type:'set', data: 값}`으로 보냄(`cloud.js:199`). 서버는 `value`를 읽으므로 **저장되지 않는다**.
2. 받기: `action.data`를 읽음(`cloud.js:163`) → 다른 사람의 값이 `undefined`.
3. 소켓이 열리기 전 쓰기는 버리고 다시 보내지 않음(`cloud.js:246-247`).

## 8. 재는 방법 (사용자 도구, `_work/tessvm/`)

- `tsrv.mjs`: 포트 3100에서 `ext/`와 풀린 `.ent`를 서빙. `/load?file=`로 `.ent`를 푼다.
- `ext/harness/index.html`: 확장의 `toTessProject` + `boot`를 그대로 쓰는 하네스. `window.Function`을 감싸 생성 소스(`__progSrc`, 커널은 `__kernSrc`)를 잡고, 함수 이름 표(`__fnNames`)를 만든다.
- `trun.mjs file.ent --script s.json [--gpu] [--throttle 4] [--vars a,b]`: 헤드리스 크롬(기본 소프트웨어 GL)으로 실행.
  - 단계: `wait/down/up/shot/eval/vars`, `fps`(틱 평균·최대 ms, `flush` ms), `profStart/profStop`(CPU 프로파일을 생성 소스 줄 → **엔트리 함수 이름**으로 묶어 출력), `castStart/castStop`(`cast.js`에 임시 계수기를 달았을 때 `toFixed`·`decimalsBelow` 호출 위치를 함수·줄별로 셈. 끝나면 원본 복구 — `cast.orig.js`).
- `bench-cast.mjs`: `cast.js` 연산별 ns. `kprobe.mjs`/`kslots.mjs`: 커널 루트·거절 이유·슬롯.
- `mkbench.mjs`/`mktour.mjs`: 레이싱 메뉴 조작 키 스크립트 생성.
- 측정 주의(사용자 경험):
  - 빌드끼리 **번갈아 3회** 돌려 평균(한 빌드 첫 회가 자주 튐, `RH:717`). CPU ×4 스로틀로 느린 PC 흉내.
  - Chrome 154는 같은 코드가 Node 24보다 약 25% 느리고, 헤드리스는 25초쯤 뒤 2배 느려질 때가 있다(`_work/rt/HANDOFF.md:33`).
  - `ticks/s`만 보면 속는다. 화면 갱신 수와 같이 볼 것(`_work/rt/HANDOFF.md:26`).
  - 소프트웨어 GL은 회차마다 ±5 fps(`RH:24`).
