## 1. 렌더 파이프라인 — 언제, 무엇을 다시 그리나

### 1.1 틱과 렌더는 서로 다른 타이머다

| 루프 | 코드 | 주기 |
|---|---|---|
| 엔진 틱(블록 실행) | `engine.js:559-562` `this.ticker = setInterval(this.update, Entry.tickTime)`; `tickTime = Math.floor(1000 / Entry.FPS)` | FPS 60이면 16ms, 즉 **62.5Hz** (`util/utils.js:55` 기본 60) |
| 무대 렌더 | `stage.js:152-160` `render = function stageRender(){ … Entry.stage.update(); … setTimeout(stageRender, 16 - (time % 16) + 16 * Math.floor(time / 16)) }` | 아래 1.2 |

- 틱 하나에서는 현재 장면의 모든 오브젝트 스크립트를 실행한다(`engine.js:577-585` `mapObjectOnScene(this.computeFunction)` → `script.tick()`).
- JS는 단일 스레드라서 **렌더는 틱과 틱 사이에만** 일어난다. 그래서 "지우기 → 전부 다시 그리기"를 **한 틱 안에** 끝내면 화면에는 항상 완성된 프레임만 보인다. 그리기를 여러 틱(= `반복하기` 한 바퀴마다 1틱)에 나누면 반쯤 그린 프레임이 그대로 렌더될 수 있다(깜빡임). 한 틱 안에서 끝내는 기법은 `07-runtime-quirks.md` §함수 호출은 반복하기의 60fps 틱을 우회 를 보라.
- 62.5Hz 틱 주기는 `07-runtime-quirks.md` 의 실측값 "62.5fps"와 맞는다.

### 1.2 렌더 1회가 16ms를 넘으면 렌더 주기가 3배로 뛴다

`stage.js:156-159`:
```js
let time = _.now();
Entry.stage.update();
time = _.now() - time;
Entry.stage.timer = setTimeout(stageRender, 16 - (time % 16) + 16 * Math.floor(time / 16));
```
렌더에 걸린 시간을 t, k = floor(t/16) 라고 하면 **렌더 주기 = t + 지연 = 16·(2k+1) ms** 다.

| 렌더 1회 시간 t | 렌더 주기 | 화면 fps |
|---|---|---|
| < 16ms | 16ms | 62.5 |
| 16–32ms | 48ms | **20.8** |
| 32–48ms | 80ms | 12.5 |

fps가 서서히 떨어지지 않고 **계단식으로 떨어진다**. 여기서 t는 `app.render()` 안에서 걸리는 시간이다. 붓 지오메트리 재분할(2장), 줄바꿈 글상자 래스터화(5장), 필터 캐시 생성(3.4)이 모두 이 시간에 들어간다. 블록 실행 시간은 포함되지 않는다.

### 1.3 다시 그리는 조건: `Entry.requestUpdate` 플래그 하나뿐

- `stage.js:165-189` `update()`: `if (!Entry.requestUpdate) return;` 다음에 `updateForce()` → `this._app.render()` (`stage.js:191-193`)가 **무대 전체**를 다시 그린다. 바뀐 부분만 그리는 기능(dirty-rect)은 없다.
- 거의 모든 setter가 마지막 줄에서 `Entry.requestUpdate = true` 를 켠다. 예: `setX` `entity.js:248`, `setY` `entity.js:277`, `setRotation` `entity.js:344`, `setVisible` `entity.js:1055`, `addStamp` `entity.js:1633`. 값이 그대로여도 켠다. 그래서 실행 중에는 사실상 **16ms마다 매번 전체 렌더**가 일어난다.
- 변수 값 설정은 `Entry.requestUpdateTwice = true` 로 렌더를 한 번 더 요청한다(`class/variable/variable.js:338-343`, `stage.js:184-188`).
- PIXI Application 은 `autoStart: false` 로 만든다(`class/pixi/init/PIXIGlobal.ts:43-50`). 그래서 평소에는 PIXI 자체 ticker가 렌더하지 않는다. **예외**는 1.5를 보라.

### 1.4 렌더 비용을 키우는 요인 (WebGL)

| 요인 | 근거 | 설명 |
|---|---|---|
| 표시 객체 수 | `[PIXI] 31455-31469` `Container.render` 가 자식을 전부 순회 | 오브젝트, 복제본, 도장, 붓 Graphics, 글상자, 말풍선, 변수창이 모두 객체 하나씩이다. **화면 밖에 있어도 그린다**(컬링 없음). `visible=false` 이거나 `worldAlpha<=0` 이면 건너뛴다(`[PIXI] 31457`). |
| 지오메트리가 바뀐 붓/채우기 | 2장 | 선을 하나라도 더하면 그 Graphics 의 모든 선을 다시 분할한다. |
| 바뀐 글자 | `[PIXI] 51093-51099` `Text._render → updateText(true)` | 글자 캔버스를 다시 그리고 GPU에 다시 올린다. |
| 필터 캐시 무효화 | `PIXISprite.ts:112-145` | 효과를 바꾼 다음 첫 렌더에서 스프라이트마다 오프스크린 렌더 패스가 1회씩 돈다. |
| 픽셀 수(fill-rate) | `util/init.js:447-448` 캔버스 **640×360 고정**, `PIXIGlobal.ts:48` `antialias: true` | 무대 좌표 480×270을 4/3배로 확대해 그린다(`stage.js:46-48`). GPU 픽셀 비용은 작다. 병목은 대부분 JS 쪽이다(**추정**). |
| 텍스처 아틀라스 | `class/pixi/atlas/EntryTextureOption.ts:80-90` URL에 `ss=1` 이 있을 때만 켜짐 | 기본은 그림마다 텍스처가 따로 있다. 여러 텍스처를 쓰는 스프라이트가 섞이면 배치 수가 늘 수 있다(**추정**). |

### 1.5 함정: "묻고 대답 기다리기"를 한 번 쓰면 이후 렌더가 계속 두 번씩 돈다

- `stage.js:653-667` `hideInputField()` 안에서 `GEHelper.tickByEngine()` 을 호출한다. WebGL 이면 `Entry.stage._app.ticker.start()` 가 실행된다(`GEHelper.ts:187-193`).
- PIXI Application 의 ticker 에는 `render` 가 등록되어 있다(`[PIXI] 52161` `ticker.add(this.render, …)`). 소스 전체에 `ticker.stop` 호출은 **없다**.
- 결과적으로 대답 입력이 한 번 끝난 뒤부터는 `requestUpdate` 와 상관없이 **모니터 주사율마다** 전체 렌더가 추가로 돈다. 엔트리 자체 렌더 루프도 그대로 돈다. 영상/AI 인식 블록도 같은 함수를 부른다(`GEHelper.ts:298,314,330`).
- CreateJS 모드에서는 `createjs.Ticker` 에 stage 가 tick 리스너로 붙는다. 그러면 매 tick마다 `stage.update()` 가 돌고, 붓 명령 전체를 다시 그린다(**추정**: 2.6과 같은 비용).

## 2. 붓(펜) · 채우기 · 도장 — 내부 구조와 비용

### 2.1 구조

- 붓을 처음 쓰면(`start_drawing` 또는 색/굵기 블록) `Entry.setBasicBrush` 가 Graphics 를 하나 만든다. 이 Graphics 는 **스프라이트 바로 아래** z 위치에 끼워 넣는다(`util/utils.js:1595-1634`, `addChildAt(shape, getChildIndex(sprite.object))`).
- 채우기도 별도 Graphics 를 같은 방식으로 만든다(`util/utils.js:1664-1683`). 둘 다 스프라이트 바로 아래에 들어가므로 **나중에 만든 쪽이 위에 놓인다**. `set_random_color`, `change_brush_transparency`, `set_brush_tranparency` 는 붓을 먼저 만들고 채우기를 나중에 만든다(`block_brush.js:244-263, 505-513, 595-614`). 그래서 이 블록으로 시작하면 채우기가 선 위를 덮는다.
- 이동 블록마다 끝에서 다음을 실행한다.
  ```js
  if (sprite.brush && !sprite.brush.stop) sprite.brush.lineTo(sprite.getX(), sprite.getY() * -1);
  if (sprite.paint && !sprite.paint.stop) sprite.paint.lineTo(sprite.getX(), sprite.getY() * -1);
  ```
  (`block_moving.js:83-88` move_direction, `:394-399` move_x, `:620-625` locate_x, `:749-754` locate_xy, `:924-929` locate 등)
  **`setX`/`setY` 자체는 선을 긋지 않는다**(`entity.js:237-250`). 선은 이동 블록이 블록 단위로 긋는다.

### 2.2 선 하나(세그먼트)가 저장되는 방식 — 선마다 독립 도형

`class/pixi/etc/PIXIBrushAdaptor.ts:90-99`:
```ts
lineTo(x, y) {
    this._shape.moveTo(this.position.x, this.position.y);
    this._shape.lineTo(Number(x), Number(y));
    this.position = { x: Number(x), y: Number(y) };
    this._shape.geometry.invalidate();
}
```
- PIXI `moveTo` 는 `startPoly()` 를 부른다. 이전 경로의 점이 2개 이상이면 그 경로를 `drawShape` 로 확정한다(`[PIXI] 36176-36189`, `36212-36216`). 그래서 **선 하나 = `GraphicsData` 하나**(Polygon 객체와 lineStyle/fillStyle 복제본을 매번 새로 할당)가 된다(`[PIXI] 35138-35151`).
- 선마다 따로 분리되므로 꺾이는 점에 join 이 없다. 굵은 선을 꺾으면 모서리에 틈이 보인다. 선 끝 모양(cap)은 기본값 **BUTT** 다(`[PIXI] 36151`). CreateJS 도 기본 `"butt"` 다(easeljs `StrokeStyle.exec`).
  - ⚠️ `07-runtime-quirks.md` §붓 라인 vs brush_stamp 은 "round cap 이라 두께/2 만큼 넘친다"고 적었다. 소스 기본값과 다르다. 원인은 규명하지 못했다. CreateJS 에서는 같은 stroke 의 선들이 한 경로로 이어져 **miter join**(miterLimit 10)이 생기므로 꺾이는 곳의 뾰족한 돌출이 원인일 수 있다(**추정**).

### 2.3 가장 중요한 비용: 선 하나만 더해도 그 붓 전체를 다시 분할한다

- `geometry.invalidate()` (`[PIXI] 35094-35115`)는 `this.shapeIndex = 0` 으로 되돌리고 points/indices/colors/uvs 배열을 모두 비운다.
- 렌더 시 `Graphics._render` → `geometry.updateBatches()` (`[PIXI] 36598-36613`, `35247-35332`)는 `for (i = this.shapeIndex; i < graphicsData.length; i++)` (`[PIXI] 35264`) 로 돌면서 shapeIndex 부터 **모든 GraphicsData 를 다시 삼각형으로 분할**(`command.build`, `processLine`)한다. 그 뒤 Uint16/Float32 배열을 새로 만들고 버퍼를 다시 올린다.
- PIXI 는 원래 새로 추가된 도형만 처리하는 증분 처리가 가능하다. 그런데 엔트리 어댑터가 `lineTo` 마다 `invalidate()` 를 불러서 그 기능을 끄고 있다.

**비용 모델 (WebGL, 붓 1개 기준)**

| 상황 | 렌더 1회 비용 |
|---|---|
| 지난 렌더 이후 새 선 없음 | 지오메트리 재생성 없음(`validateBatching`: `dirty === cacheDirty` 이면 return, `[PIXI] 35360-35363`). GPU 그리기만 한다. 싸다. |
| 새 선이 1개라도 있음 | **지우기 이후 누적된 선 N개 전부 재분할**, O(N) |
| 매 프레임 "모두 지우기 → N개 다시 그리기" | 어차피 O(N) 이다. 추가 손해는 없다. |
| 지우지 않고 계속 쌓으며 조금씩 추가(점진 렌더) | 프레임마다 O(누적 N). 전체로는 **O(N²)** 가 된다. 레이 트레이서가 여기서 가장 크게 손해 본다. |

- 렌더 1회의 분할 시간이 16ms를 넘으면 1.2의 절벽이 생긴다.
- 색이 여러 가지여도 큰 Graphics 는 draw call 이 1개다. 색은 정점 색으로 처리된다(`[PIXI] 35418-35496` `buildDrawCalls`: 텍스처로만 그룹을 나누고 `addColors`). 점이 100개 미만인 작은 Graphics 는 배치 렌더러로 합쳐진다(`[PIXI] 35400-35412` `BATCHABLE_SIZE = 100`).
- 붓 결과를 비트맵으로 캐시하는 단계는 **없다**. 소스에서 `cacheAsBitmap`/`cache()` 는 효과 필터용으로만 쓰인다(`entity.js:1289,1679`).

### 2.4 길이 0인 이동은 아무것도 그리지 않는다 (점 찍기 주의)

- PIXI `lineTo` 는 직전 점과 같으면 점을 추가하지 않는다(`[PIXI] 36226-36235`). 점이 1개뿐인 경로는 `startPoly` 의 `len > 2` 검사를 통과하지 못하고 버려진다(`[PIXI] 36179-36181`).
- 그래서 붓을 내린 상태로 **제자리 이동은 점을 남기지 않는다**. 픽셀 하나를 찍으려면 최소 길이로 움직여야 한다. 예: 굵기 1로 (x, y) → (x+1, y) 로 그리면 1×1 사각형이 된다(BUTT cap 기준).

- 투명도 100%(alpha 0)인 선은 `visible=false` 스타일이 되어 지오메트리를 만들지 않는다(`[PIXI] 36157-36159`).
- 하지만 `lineTo` 의 `invalidate()` 는 그대로 불리므로 재분할 비용은 그대로 든다.

### 2.6 CreateJS 모드에서 붓 비용

- 붓이 `createjs.Graphics` 다(`GEHelper.ts:887-893`). 선마다 명령(instruction)이 쌓인다.
- `stage.update()` 는 Shape 마다 명령 전체를 canvas 2D 에 **매 렌더마다 다시 실행**한다. 새 선이 있든 없든 마찬가지다. 즉 렌더마다 O(누적 선 수)다(**추정**: easeljs 기본 동작이고 캐시를 쓰지 않으므로).
- 같은 stroke 안의 선들은 하나의 path 로 이어진다. 그래서 꺾이는 곳에 miter join 이 생긴다(**추정**).

### 2.7 채우기 (`start_fill` / `stop_fill` / `set_fill_color`)

- 블록 팔레트에 노출되어 있다(`extern/util/static.js:138-140`).
- `class/pixi/etc/PIXIPaintAdaptor.ts:61-78`: 채우는 동안 이동할 때마다 **같은 Polygon 에 점을 추가**하고 `invalidate()` 한다. 다각형 하나(= 삼각형 하나)가 `GraphicsData` 하나이고, 렌더할 때 earcut 으로 삼각분할한다(**추정**: PIXI 5 Polygon fill 은 earcut).
- 채우기 Graphics 의 선 굵기는 undefined → 0 이므로 외곽선은 그리지 않는다(`PIXIPaintAdaptor.ts:86-91`, `[PIXI] 36157`).
- 삼각형 하나를 채우는 최소 순서:
  1. 채우기가 멈춘 상태에서 꼭짓점 1로 이동
  2. `start_fill` (`block_brush.js:109-122`: 색 문자열 생성·파싱 후 `moveTo`)
  3. 꼭짓점 2, 꼭짓점 3으로 이동 (다각형은 자동으로 닫히므로 1로 돌아갈 필요 없다)
  4. `stop_fill` (`:143-150`)
- 붓이 내려가 있으면 같은 이동마다 **붓 선도 같이** 생긴다(2.1). 외곽선이 필요 없으면 붓을 멈춰 둔다.
- ⚠️ **채우기를 여러 틱에 걸쳐 하지 마라 (추정)**. 렌더 때 PIXI `finishPoly()` 가 진행 중인 경로를 `drawShape` 로 확정하고 `currentPath=null` 로 만든다(`[PIXI] 36195-36204`, `36599`). 그런데 어댑터는 자기 `this.currentPath` 로 같은 Polygon 을 계속 붙잡고 있다가 다시 넣는다(`PIXIPaintAdaptor.ts:65-75`). 그래서 렌더를 한 번 넘길 때마다 같은 다각형이 `graphicsData` 에 **한 번 더** 들어간다. 반투명 채우기는 점점 진해지고 비용도 늘어난다.
- `set_fill_color` 도 `endFill → beginFill → moveTo` 를 한다(`block_brush.js:310-329`). 색이 직전과 같으면 생략하는 편이 낫다.

### 2.8 도장 찍기 (`brush_stamp`)

`entity.js:1627-1634`:
```js
addStamp() {
    const stampEntity = new Entry.StampEntity(this.parent, this);
    stage.loadEntity(stampEntity, stage.selectedObjectContainer.getChildIndex(this.object));
    this.stamps.push(stampEntity);
```
- **생성 비용이 크다.** `StampEntity` 는 `EntityObject` 를 상속한다(`class/stamp_entity.js:15-35`). 그래서 생성자 전체(`entity.js:21-130`)가 돈다: 빈 스프라이트, ScaleAdaptor, 이벤트 리스너 3개, 드래그 핸들러. 그 뒤 `GEHelper.cloneStamp` 로 스프라이트를 **하나 더** 만든다(`GEHelper.ts:142-169`).
- **삽입이 O(무대 자식 수)다.** `getChildIndex` 는 indexOf, `addChildAt` 은 splice 다(`[PIXI] 31186-31199`, `31228`).
- 도장은 지울 때까지 **표시 객체로 계속 남는다.** 렌더할 때마다 하나씩 순회한다.
- **지우기가 O(N × 자식 수)다.** `removeStamps` 는 도장마다 `destroy` → `unloadEntity` → `removeChild` (indexOf + splice) 를 한다(`entity.js:1636-1640`, `1642-1673`, `[PIXI] 31268-31296`). 도장 N개를 매 프레임 지우고 다시 찍으면 대략 O(N²) 다.
- **효과가 걸린 상태로 찍으면** 도장마다 `applyFilter()` 를 하므로(`stamp_entity.js:27-30`) 도장마다 RenderTexture 와 필터 패스가 하나씩 생긴다(3.4).
- 도장은 원본의 `visible` 을 복사한다(`GEHelper.ts:147`). 숨긴 상태로 찍으면 보이지 않는다(`07-runtime-quirks.md` 와 일치).
- **복제본이 찍은 도장과 그린 선은 그 복제본이 삭제될 때 함께 사라진다**(`entity.js:1660-1665`: `removeStamps`, `removeBrush`, `removePaint`).
- 실측 참고(CreateJS, 로컬 하네스): 프레임당 도장 약 250개가 60fps 의 경계다(`07-runtime-quirks.md` §brush_stamp 타일 렌더러). 위 O(N·자식) 구조와 들어맞는다.

### 2.9 수천 개 삼각형·픽셀을 싸게 그리는 법 (정리)

## 3. 엔티티 setter 비용

### 3.1 setter 별 부수 효과

| setter | 하는 일 | 근거 |
|---|---|---|
| `setX` / `setY` | `object.x/y` 대입 → `updateCoordinateView` (원본이고 **편집기에서 선택된 오브젝트일 때만** DOM 입력창 갱신) → `updateDialog` (말풍선이 있으면 bounds 재계산) → `requestUpdate` | `entity.js:237-250`, `266-279`; `object.js:250-275`; `entity.js:1329-1334` |
| `setRotation` | rotateMethod 가 `'free'` 가 아니면 0으로 강제 → mod 360 → `updateDialog` → `updateRotationView` → `dispatchEvent('updateObject')` (실행 중에는 리스너가 제거되어 있다, `stage.js:130-132`) | `entity.js:333-346` |
| `setDirection` | 회전방식이 `'vertical'` 이고 좌우가 바뀌면 `setScaleX(-…)` + `stage.updateObject()` | `entity.js:308-327` |
| `setScaleX/Y` | ScaleAdaptor 갱신 → `updateCoordinateView` (복제본도 호출됨) → `updateDialog`. **글상자(WebGL)는 `setFontScaleX/Y` → 글자를 다시 래스터화** | `entity.js:415-468`; `class/pixi/text/PIXIText.js:41-52` |
| `setSize` | `getSize` 계산 + `setScaleX` + `setScaleY` (위 비용 × 2) | `entity.js:477-483` |
| `setVisible` | `object.visible` 대입. 말풍선 표시 동기화 | `entity.js:1048-1058` |
| `setImage` (모양 바꾸기) | `getPicture` (id 비교 → 이름 비교 → 번호 순서로 **선형 탐색**, `object.js:342-372`) → `setWidth/Height/ScaleX/ScaleY/RegX/RegY` → 텍스처 맵 조회(`PIXIAtlasManager.ts:53-65`) → `refreshFilter` (**필터가 걸려 있으면 다음 렌더에서 필터 패스 1회**) | `entity.js:1071-1131`; `PIXISprite.ts:94-102` |

- 모양 텍스처는 오브젝트를 만들 때 **모든 모양을 미리 요청**한다(`object.js:68-77`). 실행 중 모양을 바꿀 때 로딩으로 멈추는 일은 없다.
- 640×360 보다 큰 그림은 텍스처가 자동으로 축소된다(`PIXIAtlasHelper.ts:54-67`, `EntryTextureOption.ts:32-41`).

### 3.2 붓을 내렸을 때와 올렸을 때

- 붓을 올리면(`stop=true`) 이동 블록의 `lineTo` 분기를 건너뛴다. 남는 비용은 setter 비용뿐이다.
- 붓을 내리면 **이동 블록 하나마다 선 1개 + 붓 전체 무효화**가 생긴다(2.3).

### 3.3 `x 위치 정하기` + `y 위치 정하기` 대신 `x: y: 위치로 이동하기`

| 블록 구성 | setter | 붓을 내렸을 때 선 |
|---|---|---|
| `locate_xy` 1개 | `setX` + `setY` (`block_moving.js:742-756`) | **1개** (대각선) |
| `locate_x` + `locate_y` | `setX` + `setY` (`block_moving.js:617-627` + `locate_y`) | **2개** (ㄱ자 모양. 그림도 달라진다) |

- 붓을 올렸을 때 두 방식의 setter 비용은 같다. 블록 실행 비용만 1개냐 2개냐의 차이다.
- `locate_xy` 는 `Number(value)` 로 변환한다. 빈 문자열은 0, 숫자가 아닌 문자는 NaN 이 된다(`block_moving.js:743-745`).

### 3.4 효과(색깔/밝기/투명도) 비용

`entity.js:1138-1290` `applyFilter(isForce, forceEffects)`:
- 블록에서는 항상 `applyFilter(true, [effectName])` 로 부른다(`block_looks.js:516, 619`).
- `diffEffects` = 초기값과 다른 **모든** 효과 + 강제 지정 효과(`entity.js:1142-1150`).
- **색깔(hsv)·밝기**: 호출할 때마다 `new ColorMatrixFilter` 를 새로 만든다(`entity.js:1155-1270`, `GEHelper.ts:785-835`). WebGL 이면 `setFilterAndCache` 가 무효화 표시를 한다. 다음 렌더에서 `renderer.batch.flush()` 후 오프스크린 렌더 1회를 하고, 결과를 **스프라이트 전용 RenderTexture** 에 저장한다(`PIXISprite.ts:71-88, 112-145`). 이후 프레임에서는 캐시된 텍스처를 쓴다.
- **투명도**는 `obj.alpha` 대입만 한다. 필터를 쓰지 않는다(`entity.js:1272-1281`). **다만 색깔이나 밝기가 이미 걸려 있으면** 투명도만 바꿔도 diffEffects 에 그 효과들이 들어가므로 필터를 다시 만들고 다시 렌더한다.
- 투명도가 0.001 미만이면 `interactive=false` 가 되어 클릭되지 않는다(`entity.js:1276-1280`). 렌더에서도 건너뛴다(`[PIXI] 31457`). **충돌 판정에는 여전히 걸린다**(6장).
- CreateJS 에서는 효과를 바꿀 때마다 `object.cache()` 를 하고 CPU 로 픽셀 필터를 적용한다(`entity.js:1289, 1675-1683`, `GEHelper.ts:842-848`). 비용이 이미지 크기에 비례한다(**추정**).
- 복제본을 만들 때 원본 효과를 복사해서 `applyFilter()` 를 한다(`object.js:553-556`). 효과가 걸린 원본을 복제하면 복제본마다 RenderTexture 가 하나씩 생긴다.

결론: **매 프레임 색깔/밝기를 바꾸는 복제본이 많으면** 그 수만큼 필터 패스와 객체 할당이 생긴다. 색이 다른 모양을 미리 만들어 두고 모양만 바꾸는 편이 싸다. 단 필터가 이미 걸린 스프라이트는 모양을 바꿀 때도 필터 패스가 돈다(3.1).

## 4. 복제본

### 4.1 한도

- `util/init.js:63` `this.maxCloneLimit = 360;`
- `object.js:541` `if (this.clonedEntities.length > Entry.maxCloneLimit) return;` 비교가 `>` 이므로 **오브젝트 하나당 최대 361개**다. 한도는 오브젝트별이다(`clonedEntities` 는 오브젝트마다 따로 있다).
- 넘으면 **오류 없이** 생성이 무시된다. 도장은 `clonedEntities` 에 들어가지 않으므로 한도와 무관하다(`entity.js:1627-1634`).

### 4.2 생성 비용 (`object.js:540-578`)

1. `new Entry.EntityObject(this)`: 스프라이트, ScaleAdaptor, 이벤트 리스너 3개, 드래그 핸들러(`entity.js:21-130`).
2. `entity.toJSON()` 으로 원본을 직렬화한 뒤 `injectModel` 을 호출한다. 여기서 `setImage` 와 `syncModel_` 의 setter 약 16개가 실행되고, setter 마다 `updateDialog`/`requestUpdate` 를 한다(`entity.js:136-196`, `1389-1421`).
3. 효과 복사 + `applyFilter()` (3.4).
4. `raiseEventOnEntity(…'when_clone_start')`: `when_clone_start` 스크립트마다 `new Entry.Executor` (`engine.js:979-985`, `playground/code.js:123-144`).
5. `addCloneVariables`: 그 오브젝트의 **지역 변수·지역 리스트를 전부 복제**한다. 리스트는 `JSON.parse(JSON.stringify(array))` 로 깊은 복사한다(`object.js:662-669`, `class/variable/variable.js:552-554`, `class/variable/listVariable.js:523-530`). **큰 지역 리스트가 있는 오브젝트를 복제하면 복제본마다 리스트 전체를 복사한다.**
6. `getChildIndex` (O(자식 수)) + `addChildAt` (splice) (`object.js:569-575`).
7. 원본에 붓이 있으면 `setCloneBrush` 로 **복제본 전용 Graphics 를 하나 더** 만든다(`object.js:576-578`, `util/utils.js:1637-1662`). 복제본이 선을 긋지 않아도 표시 객체가 하나 늘어난다.
8. **글상자 복제본은 특히 비싸다.** `injectModel` → `setFont` 가 `syncFont` 를 여러 번 부르고, 각각이 `Entry.stage.update()` 로 **무대 전체를 동기 렌더**한다(5.2). `new PIXIText` 는 DOM 에 `<canvas>` 를 하나 추가한다(`PIXIText.js:12-22`).

### 4.3 삭제 비용

- `removeClone` (`entity.js:1361-1379`): `clonedEntities.indexOf` + `splice` → O(복제본 수).
- `clearExecutorsByEntity`: 그 오브젝트의 모든 실행기를 순회한다(`playground/code.js:242-248`). 끝난 실행기는 다음 틱에 배열에서 빠진다(`code.js:182-188`).
- `destroy` (`entity.js:1642-1673`): 도장 전부 삭제, 말풍선 제거, 붓·채우기 Graphics 삭제, `removeChild` (indexOf), PIXI destroy.
- `remove_all_clones` 는 배열 복사본에서 하나씩 `removeClone` 한다(`block_flow.js:851-858`). 앞에서부터 splice 하므로 O(n²) 지만 n ≤ 361 이라 작다.

### 4.4 실행 중 비용

- 복제본 하나 = 스프라이트 1개(+ 붓 Graphics + 말풍선)이고 렌더마다 순회한다(1.4).
- 복제본의 스크립트는 부모 오브젝트의 `executors` 배열에서 매 틱 실행된다(`playground/code.js:154-190`).

### 4.5 권장

- **풀링**: 필요한 수만큼 시작할 때 한 번 만든다. 이후에는 `숨기기/보이기` 와 이동으로 재사용한다. 생성·삭제를 반복하면 4.2와 4.3 비용을 매번 낸다.
- 복제할 오브젝트에는 **큰 지역 리스트를 두지 않는다.** 데이터는 전역 리스트로 옮긴다.
- 쓰지 않는 복제본은 `숨기기`. 화면 밖으로 옮겨도 렌더 순회에서 빠지지 않는다(`[PIXI] 31455-31469`, 컬링 없음).
- 붓을 쓰는 오브젝트를 복제하면 복제본마다 Graphics 가 생긴다. 붓 오브젝트와 복제용 오브젝트를 분리한다.

### 5.1 글 쓰기 / 덧붙이기 (`text_write`, `text_append`, `text_prepend`)

- 문자열이 같으면 PIXI `text` setter 가 바로 return 한다(`[PIXI] 51320-51326`). 이때는 래스터화하지 않는다. 그래도 `updateBG` (배경 Graphics `clear` + `drawRect`, `entity.js:1530-1558`)와 `updateObject` 는 매번 실행된다.
- 문자열이 다르고 **한 줄 모드**(`lineBreak=false`)면 `getMeasuredWidth()` → `updateText(true)` 가 **즉시** 래스터화한다(`PIXIText.js:54-57, 93-260`). 순서는 `TextMetrics.measureText` → 캔버스 크기 재설정(재할당) → 줄마다 `fillText` → 텍스처 update 이벤트 → 다음 렌더에서 GPU 재업로드다. **한 틱에 글상자를 N번 쓰면 N번 래스터화한다.** `text_append` 도 한 번에 한 번씩 한다.
- **줄바꿈 모드**(`lineBreak=true`)면 측정을 건너뛴다. 래스터화는 렌더 때 `Text._render → updateText(true)` 에서 **한 번만** 한다(`[PIXI] 51093-51099`). 한 틱 안에서 여러 번 써도 비용은 1회다(**추정**: 소스상 그렇게 동작한다).
- 글자 캔버스 크기 ≈ (글자폭 + 10) × 1.53 × scaleX (`PIXIText.js:126-131`, `PIXIText.STAGE_SCALE = 1.53` `:331`). **크기를 키운 글상자는 래스터 비용도 커진다.** 크기를 바꿀 때마다 다시 래스터화한다(3.1).

### 5.2 글꼴·굵게·기울임 변경 = 무대 전체를 동기 렌더 여러 번

- `setFont` (`entity.js:688-733`)은 안에서 `Entry.stage.update()` 를 2번 직접 호출한다(`:722, :731`). 또 `setFontBold`/`setFontItalic`/`setFontSize`/`setFontType` → `syncFont` (`:745-763`)가 각각 `Entry.stage.update()` (`:749`)를 부른다.
- 각 호출은 `requestUpdate` 가 켜져 있으면 **`app.render()` 를 즉시 실행**한다(`stage.js:165-193`). setter 들이 그 사이에 `requestUpdate` 를 다시 켜므로 블록 하나에 전체 렌더가 여러 번 일어날 수 있다.
- 해당 블록: `text_change_font` (`block_text.js:306-309`), `text_change_effect` (`:268-272` → `entity.js:859-917`). 글상자 복제(4.2)도 같은 경로를 탄다.
- 권장: 실행 중에 글꼴이나 굵게를 바꾸지 않는다. 스타일이 다른 글상자를 미리 만들어 두고 보이기/숨기기로 바꾼다.

### 5.3 글자 색·배경 색

- `setColour` 는 `style.fill` 만 바꾼다(`entity.js:586-594`, `GEHelper.ts:852-858`). 래스터화는 다음 렌더에서 1회 일어난다.
- `setBGColour` 는 배경 Graphics 를 다시 그린다(`entity.js:618-624`). 둘 다 비교적 싸다.

### 5.4 말하기 (`dialog`, `dialog_time`)

- 블록을 실행할 때마다 `new Entry.Dialog` 를 만든다(`block_looks.js:144, 271`). 컨테이너, `PIXIText` (**DOM `<canvas>` 추가**), 테두리 Graphics, 꼬리 Graphics 를 새로 생성한다(`class/dialog.ts:23-51, 400-458`). 생성 중에 bounds 를 계산하면서 래스터화도 한다.
- 이전 말풍선은 `remove(true)` 로 무대에서 **떼기만 하고 destroy 하지 않는다**(`dialog.ts:182-189`, `stage.js:259-261`). `PIXIText` 의 canvas 는 `#textCanvasContainer` (`util/init.js:295-297`, display:none) 에 붙은 채 남는다. canvas 를 지우는 코드는 `PIXIText.destroy` 에만 있다(`PIXIText.js:323-327`). → **말하기를 반복할수록 DOM canvas 가 쌓인다**(누수). GPU 텍스처는 PIXI 텍스처 GC 가 나중에 회수할 수 있다(**추정**).
- 말풍선이 달린 오브젝트는 `setX`/`setY`/`setScale` 마다 `dialog.update()` 가 bounds 를 다시 계산한다(`entity.js:1329-1334`, `dialog.ts:142-180`).
- 메시지는 15자마다 줄바꿈한다(`dialog.ts:42`).
- 권장: 자주 바뀌는 값(디버그 수치, 점수)은 **말하기가 아니라 글상자**로 표시한다.

### 5.5 변수 표시창

- `setValue` 마다 `updateView()` 가 돈다. 보이는 변수면 값 글자를 바꾸고 `getMeasuredWidth` 로 **즉시 래스터화**하며 박스 Graphics 2개를 다시 그린다(`class/variable/variable.js:184-236, 336-343`).
- 무거운 루프에서 갱신하는 변수는 숨겨 둔다.

## 6. 충돌 판정 비용

### 6.1 `reach_something` (`block_judgement.js:162-233`)

| 대상 | 방식 | 근거 |
|---|---|---|
| 자신이 숨김 | 바로 false | `:163-165` |
| 벽(위/아래/좌/우) | 벽 스프라이트(`bound.png` 확대본)와 **픽셀 충돌**. `wall` 이면 최대 4회 | `:172-189`; `stage.js:526-547` |
| 마우스 포인터 | `GEHelper.hitTestMouse`: PIXI hitTest → 스프라이트 bounds 안이면 1×1 `drawImage` + `getImageData` | `GEHelper.ts:171-185`; `class/pixi/plugins/PIXIPixelPerfectInteractionPlugIn.js:30-85` |
| 글상자가 한쪽이라도 있음 | 변환된 **AABB 사각형** 겹침만 검사(회전하면 실제보다 큼) | `block_judgement.js:194-213`; `util/utils.js:1350` |
| 스프라이트 ↔ 스프라이트 | 원본(보이면) 1회 + **대상 오브젝트의 모든 복제본**을 순회하며 픽셀 충돌. 처음 맞는 것에서 종료 | `:214-230` |

### 6.2 픽셀 충돌 본체 (`class/pixi/etc/PIXI-ndgmr.Collision.js:129-198`)

1. 두 객체의 `getBounds(false)` 를 구한다. 매번 transform 체인을 갱신한다. 복제본 루프에서는 **자기 자신의 bounds 도 복제본마다 다시 계산**한다.
2. 거리 사전검사와 AABB 교차 영역을 계산한다. 겹치지 않으면 여기서 끝난다(싸다).
3. 겹치면 두 객체 각각에 대해 교차 영역 크기의 2D 캔버스를 **크기 재설정(재할당)** → 변환 적용 → 원본 텍스처 `drawImage` → **`getImageData`** 를 한다(`:60-92`). 교차 영역은 화면 픽셀 단위(무대 좌표 × 4/3)다.
4. 알파 > 0.2×255 인 픽셀이 양쪽에서 처음 겹치는 곳에서 종료한다(`:275-334`).

- 비용 = O(대상 복제본 수 × bounds 계산) + O(겹친 면적 × 2) 다. 큰 스프라이트끼리 많이 겹치면 수십만 바이트를 할당하고 읽는다.
- 원본 텍스처(`internal_getOriginalTex`)로 판정하므로 **효과(투명도, 색)는 무시**된다. 투명도 100% 여도 보이기 상태면 충돌한다(`block_judgement.js:163` 은 `getVisible()` 만 검사).
- CreateJS 모드는 `window.ndgmr` 로 vendor 의 easeljs 용 ndgmr 을 쓴다. 이 파일은 PIXI 전용이다(`PIXIGlobal.ts:30-31`). 알고리즘은 같은 계열이다(**추정**).

### 6.3 권장

- 총알·적이 많으면 블록으로 **좌표 거리(원/사각형) 계산**을 한다. `reach_something` 은 대상 복제본 전체를 픽셀 검사할 수 있다.
- 꼭 써야 하면 대상 오브젝트의 복제본 수를 줄이고, 스프라이트 크기(교차 면적)를 작게 한다.
- `bounce_wall` (`block_moving.js:93-…`)도 벽 픽셀 충돌을 최대 4회 한다.
